## Module 1 — Introduction and system structures

### What an operating system does

An **operating system (OS)** is the program that manages the hardware and provides an environment in which other programs run. Two views:

- **User view** — make the computer convenient to use (a GUI, a shell).
- **System view** — act as a **resource allocator** (CPU time, memory, files, I/O devices) and a **control program** that prevents errors and misuse.

The part that is always running is the **kernel**; everything else is a system program or an application.

### Computer system organisation and architecture

The CPU and device controllers share memory through a common bus. A device controller signals completion with an **interrupt**: the CPU saves its state, jumps to the **interrupt service routine** through the **interrupt vector**, then resumes. **DMA** (direct memory access) lets a controller move a whole block to memory with one interrupt per block instead of one per byte.

Storage forms a **hierarchy** — registers, cache, main memory, SSD/disk, tape — faster and smaller at the top, slower and larger at the bottom; **caching** keeps copies of hot data higher up.

Architectures: **single-processor**, **multiprocessor** (symmetric SMP or asymmetric; more throughput, economy of scale, reliability), and **clustered** systems (several machines sharing storage, often for high availability).

### Operating-system operations

- **Multiprogramming** keeps several jobs in memory so the CPU always has one to run; **time sharing (multitasking)** switches between them so fast that each user feels they have the machine.
- **Dual-mode operation:** a **mode bit** separates **user mode** from **kernel mode**. **Privileged instructions** run only in kernel mode; a user program asks for them through a **system call** (a trap).
- A **timer** interrupt stops a program from holding the CPU forever.

The OS is responsible for **process management**, **memory management**, **storage management** (file system, mass storage, caching, I/O), and **protection and security**.

### Computing environments

Traditional desktop/servers, **mobile**, **distributed** systems (networked machines sharing resources), **client–server** and **peer-to-peer**, **virtualisation**, **cloud computing**, and **real-time embedded** systems (hard deadlines, special-purpose).

### OS services and system calls

Services for users: user interface (CLI, GUI, batch), program execution, I/O operations, file-system manipulation, communication, error detection. Services for the system: resource allocation, accounting, protection.

A **system call** is the programming interface to those services, usually reached through an **API** (e.g. POSIX). Parameters pass in registers, in a memory block whose address is in a register, or on the stack.

Types of system calls: **process control** (`fork`, `exec`, `exit`, `wait`), **file management** (`open`, `read`, `write`, `close`), **device management**, **information maintenance** (`getpid`, time), **communication** (pipes, shared memory, sockets), **protection**.

**System programs** (file managers, compilers, editors, status tools) sit between the kernel and applications.

### OS design and structure

Separate **policy** (what to do) from **mechanism** (how to do it). Structures:

- **Simple / monolithic** (MS-DOS, early UNIX) — fast but hard to maintain.
- **Layered** — each layer uses only the one below; easy to debug, slower.
- **Microkernel** (Mach) — minimal kernel; services run in user space and talk by message passing; reliable but adds overhead.
- **Modules** (Linux, Solaris) — a core kernel loads components at run time.
- **Hybrid** systems mix these.

A **virtual machine** abstracts the hardware so several OSes run side by side on one machine. **System boot:** a **bootstrap loader** in firmware loads the kernel, which then starts the system. **OS generation (SYSGEN)** configures an OS for a specific machine; **debugging** uses log files, core dumps and tracing tools.

## Module 2 — Processes, threads and CPU scheduling

### Process concept

A **process** is a program in execution: code (text), data, heap, stack, plus the program counter and registers. States: **new → ready → running → waiting → terminated**. The OS records each process in a **process control block (PCB)** — state, PC, registers, scheduling information, memory limits, open files.

### Process scheduling

Queues: **job queue**, **ready queue**, **device queues**. Schedulers:

- **Long-term (job) scheduler** — chooses which jobs enter memory; controls the degree of multiprogramming.
- **Short-term (CPU) scheduler** — chooses the next ready process; runs very often.
- **Medium-term scheduler** — swaps processes out and back in.

A **context switch** saves the PCB of the running process and loads another's; it is pure overhead.

### Operations on processes

A parent creates children (`fork()` in UNIX copies the parent; `exec()` replaces the image). The parent may `wait()` for a child. A finished child whose parent has not called `wait()` is a **zombie**; one whose parent has exited is an **orphan** (adopted by `init`).

### Inter-process communication

Cooperating processes share data through **shared memory** (fast; processes synchronise themselves) or **message passing** (`send`/`receive`; simpler for distributed systems). Message passing may be **direct** or via **mailboxes/ports**, **blocking (synchronous)** or **non-blocking**, with zero, bounded or unbounded buffering. The **producer–consumer** problem is the standard example.

### Threads

A **thread** is a unit of CPU use inside a process — its own PC, registers and stack, sharing code, data and files with sibling threads. Benefits: responsiveness, resource sharing, economy, scalability on multicore.

**Multithreading models:** **many-to-one** (many user threads on one kernel thread; one block stops all), **one-to-one** (each user thread is a kernel thread — Linux, Windows), **many-to-many**. **Thread libraries:** Pthreads, Windows threads, Java threads. **Threading issues:** semantics of `fork`/`exec`, cancellation (asynchronous vs deferred), signal handling, thread pools, thread-specific data.

### CPU scheduling

Process execution alternates **CPU bursts** and **I/O bursts**. Scheduling is **non-preemptive** if a process keeps the CPU until it blocks or ends, **preemptive** otherwise. The **dispatcher** does the switch; its delay is **dispatch latency**.

Criteria: maximise **CPU utilisation** and **throughput**; minimise **turnaround time**, **waiting time** and **response time**.

| Algorithm | Idea | Notes |
|---|---|---|
| FCFS | First come, first served | Simple; **convoy effect** behind long jobs |
| SJF | Shortest next CPU burst first | Optimal average waiting time; burst must be predicted (exponential averaging) |
| SRTF | Preemptive SJF | Preempts when a shorter job arrives |
| Priority | Highest priority first | **Starvation** — fixed by **aging** |
| Round Robin | Fixed **time quantum**, then back of the queue | Good response; too small a quantum → too many switches |
| Multilevel queue | Separate queues (e.g. foreground/background) | Each queue has its own algorithm |
| Multilevel feedback queue | Processes move between queues | Most general; most complex |

For exam numericals, draw the **Gantt chart**, then compute for each process *waiting time = turnaround time − burst time* and *turnaround time = completion time − arrival time*, and average them.

**Thread scheduling** distinguishes process-contention scope (user level) from system-contention scope (kernel). **Multiprocessor scheduling** covers asymmetric vs symmetric multiprocessing, **processor affinity**, and **load balancing** (push and pull migration).

## Module 3 — Synchronisation and deadlocks

### The critical-section problem

When processes share data, the outcome may depend on the order of execution — a **race condition**. The code that touches shared data is the **critical section**. A solution must give:

1. **Mutual exclusion** — at most one process in its critical section.
2. **Progress** — if none is inside, the choice of who enters next cannot be postponed forever.
3. **Bounded waiting** — a limit on how many times others enter before a waiting process does.

### Peterson's solution (two processes)

```c
flag[i] = true;  turn = j;
while (flag[j] && turn == j) ;   /* busy wait */
/* critical section */
flag[i] = false;
```

It satisfies all three requirements, but relies on loads and stores not being reordered, which modern hardware does not guarantee.

### Synchronisation hardware

Atomic instructions such as **TestAndSet** and **Swap (compare-and-swap)** let a process set a lock and read its old value in one indivisible step, which makes simple spin locks possible. Disabling interrupts works only on a single processor.

### Semaphores

A **semaphore** S is an integer accessed only through two atomic operations:

```c
wait(S)   { while (S <= 0) ; S--; }   /* P */
signal(S) { S++; }                    /* V */
```

A **binary semaphore (mutex lock)** is 0/1; a **counting semaphore** counts available resources. To avoid busy waiting, `wait` puts the process on the semaphore's waiting list and `signal` wakes one. Misuse causes **deadlock** (two processes waiting on each other's semaphores) or **starvation**.

### Classical synchronisation problems

- **Bounded buffer:** semaphores `mutex = 1`, `empty = n`, `full = 0`. Producer: `wait(empty); wait(mutex); add; signal(mutex); signal(full);` Consumer does the mirror image.
- **Readers–writers:** many readers may read together; a writer needs exclusive access. The first-readers version can starve writers.
- **Dining philosophers:** five philosophers, five chopsticks; picking up both naively can deadlock. Fixes: allow at most four to sit, pick up both only if both are free, or use an odd/even order.

**Monitors** package shared data with the procedures that use it; only one process is active inside at a time, and **condition variables** (`x.wait()`, `x.signal()`) handle waiting.

### Deadlocks

A set of processes is **deadlocked** when each waits for a resource held by another in the set. Four **necessary conditions** must all hold:

1. **Mutual exclusion**, 2. **Hold and wait**, 3. **No preemption**, 4. **Circular wait**.

A **resource-allocation graph** shows requests and assignments; with one instance per resource type, a cycle means deadlock.

Handling deadlocks:

- **Prevention** — make one condition impossible (e.g. request all resources at once; impose a total order on resource types to break circular wait).
- **Avoidance** — grant a request only if the system stays in a **safe state**. The **Banker's algorithm** uses `Available`, `Max`, `Allocation` and `Need = Max − Allocation`; the **safety algorithm** looks for an order in which every process can finish.
- **Detection and recovery** — allow deadlock, detect it (wait-for graph or a detection algorithm like the Banker's), then recover by terminating processes or preempting resources (choose a victim, roll back, avoid starvation).

For a Banker's numerical: compute **Need**, then repeatedly find a process whose Need ≤ Work, add its Allocation to Work, and record the **safe sequence**.

## Module 4 — Memory management and virtual memory

### Background

A program's **logical addresses** are mapped to **physical addresses** by the **MMU**; a **relocation (base) register** and a **limit register** protect each process. Address binding can happen at compile, load or execution time. **Dynamic loading** and **dynamic linking (shared libraries)** save memory.

**Swapping** moves a whole process to disk and back, letting more processes share memory at the cost of transfer time.

### Contiguous allocation

Each process gets one contiguous block. Holes are chosen by **first fit**, **best fit** or **worst fit**. Allocation suffers **external fragmentation** (free memory split into small holes; fixed by **compaction**) and **internal fragmentation** (unused space inside an allocated block).

### Paging

Physical memory is divided into fixed-size **frames**, logical memory into **pages** of the same size. A logical address is split into **page number p** and **offset d**; the **page table** maps p to a frame f, and the physical address is f × page size + d. Paging removes external fragmentation (some internal remains in the last page).

- A **TLB** (translation look-aside buffer) caches recent page-table entries. **Effective access time** = h × (TLB + memory) + (1 − h) × (TLB + 2 × memory), where h is the hit ratio.
- Protection bits and a **valid–invalid bit** per entry; pages can be **shared** (e.g. one copy of an editor's code).

Page-table structures for large address spaces: **hierarchical (multi-level) paging**, **hashed page tables**, and **inverted page tables** (one entry per frame).

### Segmentation

Memory is viewed as variable-size **segments** (main program, functions, stack, arrays). An address is (segment number, offset); the **segment table** holds a **base** and **limit** for each. It matches the programmer's view but suffers external fragmentation.

### Virtual memory

**Virtual memory** lets a process run without being entirely in memory. **Demand paging** loads a page only when it is referenced. Accessing an absent page causes a **page fault**: the OS finds a free frame, reads the page from disk, updates the table, and restarts the instruction.

**Copy-on-write** lets a parent and a child created by `fork()` share pages until one of them writes, when only that page is copied.

### Page replacement

When no frame is free, a **victim** page is replaced (written back only if its **dirty bit** is set).

- **FIFO** — replace the oldest page. Suffers **Belady's anomaly** (more frames can mean more faults).
- **Optimal (OPT)** — replace the page not used for the longest time in the future. Lowest fault rate; impossible to implement, used as a benchmark.
- **LRU** — replace the page least recently used. Good; needs counters or a stack.
- **LRU approximations** — reference bit, **second chance (clock)**, enhanced second chance; counting-based LFU/MFU.

For a page-replacement numerical, write the frames after every reference and count the **page faults**.

### Allocation of frames and thrashing

Frames can be allocated **equally** or **proportionally** to process size, with **global** or **local** replacement. **Thrashing** is when a process spends more time paging than executing because it does not have enough frames; it is controlled with the **working-set model** or **page-fault frequency**.

## Module 5 — File systems, mass storage and protection

### File concept and access methods

A **file** is a named collection of related information on secondary storage, with attributes (name, type, size, protection, timestamps) and operations (create, open, read, write, seek, delete, truncate). Access methods: **sequential**, **direct (relative)**, and **indexed**.

### Directories and mounting

Directory structures: **single-level**, **two-level** (one directory per user), **tree-structured** (paths, current directory), **acyclic-graph** (shared files via links), **general graph**. A file system must be **mounted** at a mount point before use. **File sharing** across users needs owner/group IDs, and across networks needs remote file systems (NFS) and consistency semantics.

### Implementing file systems

Layered structure: application programs → logical file system (metadata, **FCBs/inodes**) → file-organisation module → basic file system → I/O control → devices. In-memory structures include the mount table, directory cache, and the **system-wide** and **per-process open-file tables**.

**Directory implementation:** a **linear list** (simple, slow search) or a **hash table** (fast; needs collision handling).

**Allocation methods:**

- **Contiguous** — each file occupies consecutive blocks; fast sequential and direct access; external fragmentation; files hard to grow.
- **Linked** — each block points to the next; no fragmentation; direct access is slow; the **FAT** keeps the links in a table.
- **Indexed** — an **index block** lists all of a file's blocks; good direct access; overhead for small files. UNIX **inodes** use direct, single-, double- and triple-indirect pointers.

**Free-space management:** a **bit vector** (one bit per block), a **linked list** of free blocks, **grouping**, or **counting** (start block + run length).

### Mass-storage structure and disk scheduling

A hard disk has platters, tracks, sectors and cylinders. Access time = **seek time** + **rotational latency** + transfer time. Disk scheduling reduces seek time:

- **FCFS** — fair, often long seeks.
- **SSTF** — nearest request first; can starve far requests.
- **SCAN (elevator)** — sweep one way then back.
- **C-SCAN** — sweep one way, jump back to the start; more uniform waiting.
- **LOOK / C-LOOK** — like SCAN/C-SCAN but turn at the last request instead of the disk end.

For a numerical, list the head movement order and sum the **total cylinders moved**.

Disk management covers **low-level formatting**, partitioning, the **boot block**, and **bad-block** handling.

### Protection

**Goals:** ensure each process uses only the resources it is authorised to, as a policy demands. **Principle of least privilege:** give a program only the privileges it needs. A **domain** is a set of (object, rights) pairs a process may use; processes can switch domains.

The **access matrix** has domains as rows and objects as columns; entry (i, j) lists the rights domain i has over object j. It is implemented as a **global table**, **access lists** per object (columns), **capability lists** per domain (rows), or a **lock-key** mechanism. Special rights — **copy**, **owner** and **control** — govern how rights themselves change.
