## Module 1 — ARM embedded systems and processor fundamentals

> **In short:** ARM processors follow a **RISC** design: simple instructions that run fast, many registers, and a **load–store** architecture. ARM adds features for embedded systems such as low power, small code (**Thumb**) and conditional execution. The programmer sees **registers**, the **CPSR** status register, a **pipeline**, and a **vector table** for exceptions and interrupts.

```flow
Fetch instruction -> Decode -> Execute (ARM7 three-stage pipeline)
```

### The RISC design philosophy

**RISC (Reduced Instruction Set Computer)** simplifies instructions so each can run in a single cycle at a high clock speed. The complexity moves from the hardware to the **compiler**.

Four major RISC design rules:

1. **Instructions:** a reduced number of instruction classes, each simple and executed in one cycle; fixed-length instructions so the pipeline can fetch the next one before decoding the current one.
2. **Pipelines:** instructions are broken into small steps that run in parallel; no microcode.
3. **Registers:** a large set of **general-purpose registers**, any of which can hold data or an address.
4. **Load–store architecture:** the processor works only on data in registers. Separate **load** and **store** instructions move data between memory and registers.

**CISC** (Complex Instruction Set Computer) does the opposite: many complex, variable-length instructions, often with microcode, so the hardware is more complex and the compiler simpler.

### The ARM design philosophy

ARM is not a pure RISC design; it adapts RISC for embedded systems:

- **Low power** (battery-powered devices) and **high code density** (small, cheap memory).
- **Small die size**, so cheap chips; **hardware debug** technology.
- Departures from pure RISC:
  - **Variable cycle execution** for some instructions (load-store-multiple takes several cycles).
  - **Inline barrel shifter**: one operand can be shifted or rotated as part of another instruction.
  - **Thumb 16-bit instruction set** for better code density.
  - **Conditional execution**: most instructions run only if a condition is true, avoiding branches.
  - **Enhanced instructions**, such as DSP multiply–accumulate.

### Embedded system hardware

An ARM-based embedded device typically has:

- **ARM processor:** the core plus surrounding components that connect it to a bus.
- **Controllers:** the **interrupt controller** and the **memory controller**.
- **Peripherals:** input/output devices on the bus (timers, serial ports, USB).
- **Bus:** usually the **AMBA** (Advanced Microcontroller Bus Architecture) bus.
  - **AHB / ASB** (high-performance buses) for fast components such as memory and DMA.
  - **APB** (peripheral bus) for slower peripherals, joined to the fast bus through a **bridge**.
- **Memory:** a hierarchy from fast **cache** to slower main memory and secondary storage. Memory width (8, 16 or 32 bits) affects cost and performance; types include **ROM**, **flash**, **DRAM** and **SRAM**.

### Embedded system software

The software stack on an embedded device:

```flow
Initialisation (boot) code -> Operating system -> Device drivers -> Applications
```

- **Initialisation (boot) code:** runs first; configures the hardware, diagnoses it, and loads the OS image (booting).
- **Operating system:** an **RTOS** (real-time OS, guaranteed response times) or a **platform OS** (such as Linux, needing an MMU).
- **Device drivers:** the standard interface to peripherals.
- **Applications:** the tasks the device exists for.

### Registers

ARM has **37 registers** in total, but only **16 general registers (r0–r15)** plus the status registers are visible in any one mode.

- **r0–r12:** general-purpose.
- **r13 (sp):** **stack pointer**.
- **r14 (lr):** **link register**; holds the return address after a subroutine call (BL).
- **r15 (pc):** **program counter**.
- **CPSR:** current program status register.
- **SPSR:** saved program status register (one per exception mode), which saves the CPSR when an exception occurs.

**Banked registers:** some registers (r13, r14 and SPSR in most modes; r8–r14 in FIQ mode) have separate physical copies for each mode, which are swapped in automatically when the mode changes.

### Current Program Status Register (CPSR)

| Bits | Field | Meaning |
|---|---|---|
| 31 | **N** | Negative result |
| 30 | **Z** | Zero result |
| 29 | **C** | Carry out (unsigned overflow) |
| 28 | **V** | Signed overflow |
| 7 | **I** | 1 = IRQ interrupts disabled |
| 6 | **F** | 1 = FIQ interrupts disabled |
| 5 | **T** | 1 = Thumb state, 0 = ARM state |
| 4–0 | **Mode** | Processor mode |

**Processor modes:**

| Mode | Use | Privileged? |
|---|---|---|
| User (usr) | Normal programs | No |
| FIQ | Fast interrupt request | Yes |
| IRQ | Normal interrupt request | Yes |
| Supervisor (svc) | After reset, and software interrupts (OS kernel) | Yes |
| Abort (abt) | Failed memory access | Yes |
| Undefined (und) | Undefined instruction | Yes |
| System (sys) | Privileged mode that uses the user registers | Yes |

Only privileged modes can write to the mode and interrupt bits of the CPSR.

**Processor states:** **ARM state** (32-bit instructions), **Thumb state** (16-bit instructions) and, on some cores, **Jazelle** (Java bytecode).

### Pipeline

A pipeline lets the processor work on several instructions at once.

- **ARM7:** 3 stages: **fetch → decode → execute**.
- **ARM9:** 5 stages: fetch → decode → execute → memory → write.
- **ARM10:** 6 stages: fetch → issue → decode → execute → memory → write.

Longer pipelines raise throughput and clock speed but increase **latency** and the cost of a branch (the pipeline must be refilled).

**Pipeline characteristic:** in ARM state, the **pc points two instructions ahead** of the one executing (pc = address of the current instruction + 8), because of the three-stage fetch–decode–execute view. An instruction is not executed until it passes completely through the execute stage.

### Exceptions, interrupts and the vector table

When an exception or interrupt occurs, the processor sets the pc to a fixed address in the **vector table**. Each entry usually holds a branch to the handler.

| Exception | Vector address |
|---|---|
| Reset | 0x00000000 |
| Undefined instruction | 0x00000004 |
| Software interrupt (SWI) | 0x00000008 |
| Prefetch abort | 0x0000000C |
| Data abort | 0x00000010 |
| (Reserved) | 0x00000014 |
| IRQ | 0x00000018 |
| FIQ | 0x0000001C |

The vector table can also start at 0xFFFF0000 (high vectors) on some cores.

### Core extensions

Hardware attached around the core to add features:

- **Cache and tightly coupled memory (TCM):** cache keeps recent data close; TCM is fast SRAM at a fixed address, with predictable timing for real-time code.
- **Memory management:** none, a **memory protection unit (MPU)** with regions and access rights, or a full **memory management unit (MMU)** with virtual memory (needed by Linux).
- **Coprocessors:** extend the instruction set, for example floating point or vector processing. **CP15** controls the cache, TCM and memory management.

## Module 2 — The ARM instruction set

> **In short:** ARM instructions fall into a few classes: **data processing** (move, arithmetic, logic, compare, multiply), **branch**, **load–store**, **software interrupt**, **program status register** and **coprocessor** instructions. Almost every instruction can be made **conditional** with a suffix such as EQ or NE, and the second operand can pass through the **barrel shifter**.

```flow
Rn (first operand) -> ALU
Rm (second operand) -> Barrel shifter (LSL, LSR, ASR, ROR) -> ALU
ALU -> Result to Rd -> Update N Z C V flags (if S suffix)
```

### Data processing instructions

Format: `<instruction>{<cond>}{S} Rd, Rn, N`, where N is a register, an immediate, or a shifted register. The **S** suffix updates the condition flags.

**Move instructions:**

- `MOV Rd, N` → Rd = N
- `MVN Rd, N` → Rd = NOT N

**Barrel shifter:** shifts the second operand before the ALU uses it, at no extra instruction cost.

| Shift | Meaning | Example (x = value, y = amount) |
|---|---|---|
| LSL | Logical shift left | x << y |
| LSR | Logical shift right | x >> y (unsigned) |
| ASR | Arithmetic shift right | x >> y (keeps the sign) |
| ROR | Rotate right | rotate x right by y |
| RRX | Rotate right extended | 33-bit rotate through the carry flag |

Example: `MOV r7, r5, LSL #2` sets r7 = r5 × 4.

**Arithmetic instructions:**

- `ADD Rd, Rn, N` → Rn + N; `ADC` adds with carry
- `SUB Rd, Rn, N` → Rn − N; `SBC` subtracts with carry
- `RSB Rd, Rn, N` → N − Rn (reverse subtract); `RSC` with carry

Example: `RSB r0, r1, #0` sets r0 = −r1.

**Logical instructions:** `AND`, `ORR`, `EOR` (exclusive OR), `BIC` (bit clear: Rd = Rn AND NOT N).

**Comparison instructions** update the flags only (no destination register; no S needed):

- `CMP Rn, N` → flags from Rn − N
- `CMN Rn, N` → flags from Rn + N
- `TST Rn, N` → flags from Rn AND N
- `TEQ Rn, N` → flags from Rn EOR N

**Multiply instructions:**

- `MUL Rd, Rm, Rs` → Rd = Rm × Rs
- `MLA Rd, Rm, Rs, Rn` → Rd = (Rm × Rs) + Rn (multiply–accumulate)
- **Long multiply** gives a 64-bit result in two registers: `UMULL`, `UMLAL` (unsigned), `SMULL`, `SMLAL` (signed): [RdHi, RdLo] = Rm × Rs (+ [RdHi, RdLo]).

### Branch instructions

- `B label` → pc = label
- `BL label` → lr = address of the next instruction, pc = label (subroutine call). Return with `MOV pc, lr`.
- `BX Rm` → branch to the address in Rm and switch to Thumb state if bit 0 of Rm is 1.
- `BLX` → branch with link and exchange (switch) state.

**Conditional execution:** append a condition code.

| Suffix | Meaning | Flags |
|---|---|---|
| EQ / NE | Equal / not equal | Z = 1 / Z = 0 |
| CS (HS) / CC (LO) | Carry set (unsigned ≥) / carry clear (unsigned <) | C = 1 / C = 0 |
| MI / PL | Negative / positive or zero | N = 1 / N = 0 |
| VS / VC | Overflow / no overflow | V = 1 / V = 0 |
| HI / LS | Unsigned > / unsigned ≤ | C = 1 and Z = 0 / C = 0 or Z = 1 |
| GE / LT | Signed ≥ / signed < | N = V / N ≠ V |
| GT / LE | Signed > / signed ≤ | Z = 0 and N = V / Z = 1 or N ≠ V |
| AL | Always (default) | — |

**Example: GCD without branches inside the loop body**

```asm
gcd     CMP    r1, r2
        SUBGT  r1, r1, r2    ; if r1 > r2: r1 = r1 - r2
        SUBLT  r2, r2, r1    ; if r1 < r2: r2 = r2 - r1
        BNE    gcd           ; repeat until r1 == r2
```

### Load–store instructions

Single register transfer:

- `LDR` / `STR`: load / store a 32-bit word
- `LDRB` / `STRB`: byte; `LDRH` / `STRH`: halfword
- `LDRSB` / `LDRSH`: signed byte / halfword (sign-extended)

**Addressing modes (index methods):**

| Mode | Syntax | Address used | Base register after |
|---|---|---|---|
| Preindex with writeback | `LDR r0, [r1, #4]!` | r1 + 4 | r1 + 4 |
| Preindex | `LDR r0, [r1, #4]` | r1 + 4 | unchanged |
| Postindex | `LDR r0, [r1], #4` | r1 | r1 + 4 |

**Multiple-register transfer** (`LDM` / `STM`) moves several registers in one instruction. Addressing modes: **IA** (increment after), **IB** (increment before), **DA** (decrement after), **DB** (decrement before). Example: `LDMIA r0!, {r1-r3}` loads r1, r2, r3 from successive words at r0 and updates r0.

**Stack operations** use LDM/STM with stack names:

- **Full / empty:** sp points to the last used item (full) or the next free slot (empty).
- **Ascending / descending:** the stack grows toward higher or lower addresses.
- ARM's convention (ATPCS) is a **full descending** stack: push with `STMFD sp!, {…}` and pop with `LDMFD sp!, {…}`.

**Swap instruction:** `SWP Rd, Rm, [Rn]` atomically loads from memory and stores a register (useful for semaphores).

### Software interrupt instruction

`SWI SWI_number` causes a **software interrupt exception**. The processor:

1. switches to **supervisor mode**,
2. saves the CPSR in SPSR_svc and the return address in lr_svc,
3. jumps to the SWI vector (0x08).

It is used to call **operating system** routines from user programs. The handler reads the SWI number from the instruction (or a register) to decide which service to run.

### Program status register instructions

- `MRS Rd, CPSR` (or SPSR): copy the status register into a general register.
- `MSR CPSR_<fields>, Rm` (or an immediate): write to the status register. Fields are c (control), x (extension), s (status) and f (flags).

**Example: enable IRQ interrupts**

```asm
        MRS    r1, cpsr
        BIC    r1, r1, #0x80    ; clear the I bit (bit 7)
        MSR    cpsr_c, r1
```

### Coprocessor instructions

Extend the instruction set; the coprocessor number p0–p15 selects the coprocessor.

- `CDP`: coprocessor data processing
- `MRC` / `MCR`: move from / to a coprocessor register
- `LDC` / `STC`: load / store coprocessor registers from memory

Example: `MRC p15, 0, r10, c0, c0, 0` reads the CP15 ID register (processor identification) into r10.

### Loading constants

An ARM instruction is 32 bits, so a full 32-bit constant cannot fit inside it. Options:

- **Immediate with rotation:** an 8-bit value rotated right by an even number of bits. `MOV r0, #0xFF000000` is valid.
- `LDR Rd, =constant` **pseudo-instruction:** the assembler uses a MOV or MVN if possible; otherwise it puts the constant in a **literal pool** and loads it with a pc-relative LDR.
- `ADR Rd, label` **pseudo-instruction:** writes a nearby address into Rd (assembled as ADD or SUB with the pc).

## Module 3 — C compilers and optimisation

> **In short:** writing C that suits the ARM architecture produces smaller, faster code. Use **32-bit int** variables for local values and loop counters, write loops that **count down to zero**, keep the number of live local variables within the available registers, pass at most **four arguments** in registers, and avoid **pointer aliasing** that forces the compiler to reload values.

```flow
C source -> Compiler (register allocation, loop optimisation) -> ARM assembly -> Assembler -> Machine code
```

### Basic C data types

| C type | ARM size |
|---|---|
| char | 8 bits (**unsigned** by default in ARM C compilers) |
| short | 16 bits |
| int / long | 32 bits |
| long long | 64 bits |

**Guidelines:**

- ARMv4 and later load/store bytes and halfwords directly, but **arithmetic is done on 32-bit registers**. A `char` or `short` local variable forces the compiler to add instructions that cut the result back to 8 or 16 bits after each operation.
- **Use `int` (or `unsigned int`) for local variables, loop counters and function arguments**, even when the value is small.
- Use `char` and `short` only for **arrays and data structures in memory**, where they save space.
- Be careful with `char` being unsigned: a test such as `c >= 0` is always true.

### C looping structures

**Loops with a fixed number of iterations:** counting **down to zero** is faster. A decrementing loop ends with `SUBS` (which sets the flags) and `BNE`, so no separate compare is needed:

```c
int checksum(int *data) {
  unsigned int i;
  int sum = 0;
  for (i = 64; i != 0; i--)   /* count down: SUBS + BNE */
    sum += *(data++);
  return sum;
}
```

- Use **`i != 0`** rather than `i > 0` as the loop condition for unsigned counters.
- **Loops with a variable number of iterations:** use a `do … while` loop if you know the loop runs at least once, to avoid the check at the start.
- **Loop unrolling:** repeat the loop body several times per iteration (for example 4×) to reduce the loop overhead, at the cost of larger code. Only worth it in critical loops.

### Register allocation

The compiler tries to keep each local variable in a register. It can use up to **14 registers** (r0–r12 and r14) for variables, but some are needed for temporary values and the calling convention.

- If more variables are live at once than there are registers, the compiler **spills** some to the stack, which is slow.
- **Keep the number of live local variables in the critical part of a function to about 12 or fewer.**
- Don't take the address of a local variable (`&x`) unless needed, because the variable must then live in memory.

### Function calls

The **ARM Architecture Procedure Call Standard (AAPCS / ATPCS)** says:

- The **first four arguments** go in **r0–r3**; further arguments go on the **stack** (slower).
- The **return value** is in **r0** (r0 and r1 for 64-bit values).
- r4–r11 must be preserved by the called function.

**Guidelines:**

- Keep functions to **four or fewer arguments**. If more are needed, group them in a **structure** and pass a pointer.
- Define small functions in the same file, before they are called, so the compiler can optimise or **inline** them.
- Use `__inline` for small, performance-critical functions to remove call overhead.

### Pointer aliasing

Two pointers **alias** when they point to the same memory. The compiler must assume that a write through one pointer may change data read through another, so it **reloads** values from memory after every store.

```c
void timers(int *t1, int *t2, int *step) {
  *t1 += *step;
  *t2 += *step;   /* *step must be reloaded: t1 might point to step */
}
```

**Fix:** copy the value into a local variable first, which the compiler can keep in a register:

```c
void timers(int *t1, int *t2, int *step) {
  int s = *step;   /* read once */
  *t1 += s;
  *t2 += s;
}
```

Also avoid taking the address of local variables, and use the `restrict` keyword (C99) where supported to promise there is no aliasing.

### Portability issues

When porting C code to ARM, watch for:

- **char type:** unsigned on ARM, signed on many other platforms.
- **int type:** older code may assume 16-bit int.
- **Unaligned data pointers:** ARM may not support unaligned word accesses; use `__packed` or byte access.
- **Endian assumptions:** ARM can be little- or big-endian.
- **Function prototypes:** always declare them; ARM passes arguments differently from some platforms.
- **Bit-fields:** their layout is implementation-defined.
- **Linked lists and casts** between pointer types that change alignment.
- **Inline assembly:** not portable between compilers.
- **The volatile keyword:** needed for memory-mapped registers and variables changed by interrupts.

## Module 4 — Exception and interrupt handling, and firmware

> **In short:** an **exception** stops normal execution and makes the processor run a **handler**. ARM saves the CPSR in the SPSR, saves the return address in lr, switches to the right **mode** and jumps to the **vector table**. Interrupts (**IRQ** and the faster **FIQ**) are exceptions caused by hardware. **Firmware** is the low-level software, such as a **bootloader**, that starts the system.

```flow
Exception occurs -> Save CPSR to SPSR_mode -> Save return address in lr_mode -> Set mode bits and disable interrupts -> pc = vector address -> Handler runs -> Restore CPSR and pc
```

### Exception handling

An exception handler must deal with:

- errors, faults and external events
- saving and restoring the processor state so the interrupted code continues correctly

### ARM processor exceptions and modes

| Exception | Mode entered | Main purpose |
|---|---|---|
| Reset | Supervisor | Initialise the system |
| Undefined instruction | Undefined | Emulate missing coprocessor instructions or trap errors |
| Software interrupt (SWI) | Supervisor | Operating system calls |
| Prefetch abort | Abort | Failed instruction fetch (virtual memory) |
| Data abort | Abort | Failed data access |
| IRQ | IRQ | Normal hardware interrupt |
| FIQ | FIQ | Fast hardware interrupt |

**On entry to an exception, the processor:**

1. saves the **CPSR** into the **SPSR** of the new mode,
2. saves the **pc** (return address, with an offset) into the **lr** of the new mode,
3. sets the CPSR mode bits to the new mode (and switches to ARM state),
4. disables interrupts as needed (IRQ is always disabled; FIQ also on reset and FIQ),
5. sets the **pc** to the vector address.

### Vector table

Each vector-table entry holds one instruction, usually one of:

- `B <handler>`: a branch, within ±32 MB
- `LDR pc, [pc, #offset]`: load the handler address from memory, which reaches the whole address space
- `MOV pc, #immediate`: for some fixed addresses

### Exception priorities

When several exceptions happen at once, they are handled in this order:

| Priority | Exception | I bit | F bit |
|---|---|---|---|
| 1 (highest) | Reset | 1 | 1 |
| 2 | Data abort | 1 | — |
| 3 | FIQ | 1 | 1 |
| 4 | IRQ | 1 | — |
| 5 | Prefetch abort | 1 | — |
| 6 (lowest) | SWI and undefined instruction | 1 | — |

### Link register offsets

When an exception is taken, lr does not always hold the exact address to return to, because of the pipeline. The handler corrects it:

| Exception | Return address | Typical return instruction |
|---|---|---|
| Undefined instruction | lr | `MOVS pc, lr` |
| SWI | lr | `MOVS pc, lr` |
| Prefetch abort | lr − 4 | `SUBS pc, lr, #4` |
| Data abort | lr − 8 | `SUBS pc, lr, #8` |
| IRQ / FIQ | lr − 4 | `SUBS pc, lr, #4` |

The **S** suffix with pc as the destination also copies the SPSR back into the CPSR, restoring the mode and flags.

### Interrupts

- **Assigning interrupts:** a system designer decides which peripheral uses which interrupt. The usual approach: **FIQ for the single fastest, highest-priority source** (for example a DMA or fast data transfer) and **IRQ for everything else**; SWI is reserved for OS calls.
- **Interrupt latency:** the time from the interrupt signal to the start of its handler. It is reduced by:
  - **nested interrupt handlers**, which re-enable interrupts so a higher-priority interrupt can be served sooner,
  - **prioritisation**, so lower-priority interrupts are ignored while a higher one runs.

### IRQ and FIQ exceptions

- Both are raised by an external signal when the corresponding bit (I or F) in the CPSR is clear.
- **FIQ is faster** because:
  - it has **more banked registers (r8–r14)**, so the handler needs to save fewer registers,
  - its vector is the **last entry (0x1C)**, so the handler can start right there, with no branch,
  - it has higher priority than IRQ.
- **Enabling and disabling:** set or clear the I and F bits in the CPSR with MRS/BIC or ORR/MSR in a privileged mode.

### Basic interrupt stack design and implementation

Each mode that handles exceptions needs its own **stack**, set up during initialisation (the banked sp of each mode).

Design choices:

- **Stack size:** must hold the deepest nesting of handlers; stack overflow is a serious bug.
- **Layout:** place the stacks so that an overflow cannot overwrite the vector table or the code. The textbook compares two memory layouts; learn its diagrams and why one is safer.
- At startup, the code switches into each mode in turn (by writing the CPSR) and sets that mode's sp.

### Firmware and bootloader

**Firmware** is the deeply embedded, low-level software that interfaces the hardware with the application or OS. It:

- identifies and initialises the platform (hardware),
- provides a **hardware abstraction layer (HAL)**,
- supports debugging,
- contains the **bootloader**, which loads the OS or application image into memory and hands over control.

**Firmware execution flow:**

```flow
Set up target platform -> Abstract the hardware (HAL) -> Load a bootable image -> Relinquish control to the OS or application
```

### ARM firmware suite and Red Hat RedBoot

- **ARM Firmware Suite (AFS):** ARM's firmware package. It contains **μHAL** (micro hardware abstraction layer), which gives a common interface to hardware, and the **Angel** debug monitor.
- **Red Hat RedBoot:** an open-source firmware and bootloader based on the eCos HAL. It provides communication over serial and Ethernet, flash-ROM management (storing images), full operating-system support (loading Linux and others) and a command-line interface.

### Example: Sandstone

**Sandstone** is the textbook's minimal example firmware. It:

- takes control at reset,
- sets up the hardware (memory, LEDs, serial port),
- copies a payload (the OS or application image) and
- passes control to it.

**Sandstone code structure (steps):**

1. Take the **reset exception** (vector table code).
2. **Start initialising the hardware.**
3. **Remap memory** (move the vector table or memory map as needed).
4. **Initialise the communication hardware** (serial port).
5. **Run the bootloader:** copy the payload and **relinquish control** to it.

**Directory layout:** the sandstone source tree keeps the build files, the assembly source and the payload (the image to boot) in separate directories; see the textbook's figure for the exact names.

## Module 5 — Caches

> **In short:** a **cache** is a small, fast memory between the processor and main memory that keeps recently used instructions and data. A **cache controller** checks each address against stored **tags**; a match is a **hit**, otherwise a **miss** loads a whole **cache line** from memory. Caches differ in **associativity**, **write policy** (writeback or writethrough), **replacement policy** and **allocation policy**. On ARM, caches are controlled through **coprocessor CP15**.

```flow
Processor address -> Split into tag, set index, data index -> Look up the set -> Tag matches and valid? Hit: return data
Processor address -> Tag mismatch -> Miss -> Evict a line (write back if dirty) -> Fill line from main memory -> Return data
```

### The memory hierarchy and cache memory

| Level | Example | Speed | Size |
|---|---|---|---|
| Registers | r0–r15 | Fastest | Smallest |
| Tightly coupled memory, L1 cache | On-chip SRAM | Very fast | KB |
| L2 cache | On or off chip | Fast | Hundreds of KB |
| Main memory | DRAM | Slower | MB to GB |
| Secondary storage | Flash, disk | Slowest | Largest |

Caches work because of **locality of reference**: programs reuse recent data (**temporal**) and nearby data (**spatial**).

A **write buffer** is a small FIFO that holds data being written to main memory, so the processor doesn't have to wait for slow memory writes.

### Caches and memory management units

- A **logical (virtual) cache** sits between the processor and the MMU; it is indexed with virtual addresses, so it is fast but must be flushed on a context switch. ARM7 to ARM10 use this.
- A **physical cache** sits between the MMU and main memory and uses physical addresses. ARM11 uses this.

### Basic architecture of a cache memory

A cache has:

- **cache lines**, each holding a block of consecutive words from main memory,
- a **directory store** holding a **tag** (the upper address bits) for each line,
- **status bits**: a **valid bit** (the line holds real data) and a **dirty bit** (the line was changed and not yet written to memory).

### Basic operation of a cache controller

The cache controller splits each address into three fields:

- **tag:** compared with the stored tags
- **set index:** selects the cache line (or set)
- **data index:** selects the word (or byte) within the line

```flow
Read set index -> Check valid bit and compare tag -> Equal: cache hit, use data index to select word
Read set index -> Not equal: cache miss -> Copy line from main memory (line fill) -> Then return the word
```

### Relationship between cache and main memory

- In a **direct-mapped cache**, each main-memory address maps to **exactly one** cache line. Simple and fast, but two addresses that map to the same line keep evicting each other (**thrashing**).
- Many memory addresses share each cache line, so the tag is what tells them apart.

### Set associativity

Set associativity reduces thrashing by letting a block go into **any of several lines** in a set.

- An **n-way set-associative** cache has n lines (ways) per set.
- A **fully associative** cache lets a block go anywhere; it needs a tag comparison for every line, often with a **CAM** (content addressable memory).
- **More ways** give fewer conflict misses but need more comparisons and power.

Example: a 4 KB cache with 16-byte lines has 256 lines. Direct-mapped, it has 256 sets of one line. As **4-way set associative**, it has 64 sets of four lines.

### Write buffers

Write buffers improve performance by holding writes so the processor continues without waiting. The cache controller drains them to memory in the background. Data in the write buffer may need to be **flushed** (drained) before certain operations, such as when hardware or another processor must see the data.

### Measuring cache efficiency

- **Hit rate** = (cache hits ÷ memory requests) × 100
- **Miss rate** = 100 − hit rate
- **Hit time:** the time to access a location in the cache
- **Miss penalty:** the time to fetch a line from main memory into the cache

### Cache policy: write policy

- **Writethrough:** every write updates **both** the cache and main memory. Memory is always up to date, but there is more bus traffic. Writes usually go through the write buffer.
- **Writeback:** a write updates **only the cache** and sets the line's **dirty bit**. Main memory is updated when the line is **evicted**. Less traffic and faster, but cache and memory are temporarily different (**coherency** must be managed).

### Cache line replacement policies

When a miss needs a line and the set is full, the **victim** is chosen by:

- **Round-robin (cyclic):** a counter selects the next way in turn. Predictable.
- **Pseudorandom:** a random-number generator selects the way. Avoids worst-case patterns.
- **Least recently used (LRU):** replaces the line used longest ago. Some ARM cores support LRU-like policies.

### Allocation policy on a cache miss

- **Read-allocate:** a line is allocated (filled) only on a **read miss**. On a write miss, the data is written straight to memory.
- **Read–write-allocate:** a line is allocated on **both** read and write misses.

Writeback caches are usually read–write-allocate; writethrough caches are usually read-allocate.

### Coprocessor 15 and caches

**CP15** registers configure and control the caches, write buffer and memory management. They are accessed with `MRC` and `MCR` instructions in a privileged mode.

- **c0:** cache type and size information (read-only).
- **c1:** control register: enable or disable the caches (I and C bits), MMU and write buffer.
- **c7:** cache operations: **clean** (write dirty lines to memory) and **flush / invalidate** (mark lines invalid), for the whole cache or one line.
- **c9:** cache **lockdown**: lock code or data into the cache so it is never evicted (for predictable real-time timing).

**Clean versus flush:** cleaning a cache writes dirty data back to memory (keeps the cache contents); flushing (invalidating) throws the cache contents away. Before flushing a writeback data cache, clean it, or the changes are lost.

## Exam tips

- Draw the **CPSR** bit layout, the **register banks for each mode**, the **vector table** and the **ARM7 pipeline**; these are frequent questions.
- Write and explain short **assembly programs**: sum of an array, GCD with conditional execution, factorial, string copy, finding the largest number. Comment each line.
- Know the **addressing modes** (preindex, postindex, writeback) and the four **LDM/STM** stack modes with a diagram of the stack before and after.
- For C optimisation, give a **before and after** code pair for each guideline: data types, loops, register allocation, function calls, pointer aliasing.
- For exceptions, memorise the **priority table** and **link register offsets**, and draw the entry and exit sequence.
- For caches, draw the **cache architecture** (tag, set index, data index), explain **direct-mapped vs set-associative**, and compare **writeback vs writethrough**.
