## Module 1 — Introduction and ER modelling

> **In short:** a **DBMS** stores data once, shares it safely and answers queries. Database design starts with an **ER diagram**: **entities** (things), **attributes** (their properties) and **relationships** (how they connect).

```flow
Requirements -> ER diagram (conceptual design) -> Relational schema (logical design) -> Tables, indexes (physical design)
```

### Database and DBMS

A **database** is a logically coherent collection of related data. A **DBMS** is the software that defines, constructs, manipulates and shares databases (MySQL, PostgreSQL, Oracle).

**Characteristics of the database approach:** self-describing (the **catalog** stores metadata), **program–data independence**, **data abstraction**, multiple **views**, and **sharing with concurrency control**.

**Advantages over file systems:** controlled redundancy, restricted unauthorised access, persistent storage, efficient query processing (indexes), backup and recovery, multiple interfaces, integrity constraints, and enforced standards. A DBMS may be unnecessary for small, simple, single-user or real-time applications where its overhead is not worth it.

### Data models, schemas and instances

A **data model** is a set of concepts to describe a database's structure: **conceptual (high-level)** like ER, **representational** like the relational model, and **physical**. The **schema** is the description (changes rarely); the **instance (state)** is the data at a moment (changes constantly).

### Three-schema architecture and data independence

- **Internal level** — physical storage.
- **Conceptual level** — the whole database's entities, relationships and constraints.
- **External level** — the views of individual user groups.

**Logical data independence:** change the conceptual schema without changing external schemas or programs. **Physical data independence:** change the internal schema (e.g. add an index) without changing the conceptual schema.

### Languages and environment

**DDL** defines schemas, **DML** retrieves and updates (SQL does both), **SDL/VDL** for storage and views. Interfaces include menus, forms, GUIs, natural language, and APIs for programmers. The **database system environment** includes the stored data and catalog, the DDL compiler, query compiler and optimiser, runtime processor, concurrency control and recovery, plus utilities (loading, backup, reorganisation).

### ER model

- **Entity** — a real-world object; **entity type** — a set of similar entities.
- **Attributes:** simple vs **composite** (Name → First, Last), single-valued vs **multivalued** (phone numbers, double oval), stored vs **derived** (age from DOB, dashed oval). A **key attribute** (underlined) identifies each entity.
- **Relationship type** among entity types, with **degree** (binary, ternary).
- **Structural constraints:** **cardinality ratio** (1:1, 1:N, M:N) and **participation** — **total** (double line, every entity must participate) or **partial**.
- A **weak entity** has no key of its own; it is identified by its **owner** entity through an **identifying relationship** (double rectangle and double diamond) plus a **partial key** (dashed underline).

### Specialisation and generalisation (EER)

**Specialisation** defines subclasses of an entity type (EMPLOYEE → SECRETARY, ENGINEER); **generalisation** is the reverse. Constraints: **disjoint** (d) vs **overlapping** (o), and **total** vs **partial**. Subclasses **inherit** the attributes and relationships of their superclass.

## Module 2 — Relational model and relational algebra

> **In short:** the **relational model** stores data in tables (relations) of rows (tuples). **Keys** identify rows and link tables. **Relational algebra** (select, project, join, union, difference) is the maths behind SQL queries.

```flow
SQL query -> Relational algebra -> Select rows (σ) -> Join tables -> Project columns (π) -> Result relation
```

### Relational model concepts

A **relation** is a table; a **tuple** is a row; an **attribute** is a column with a **domain** of atomic values. The **degree** is the number of attributes; the **cardinality** is the number of tuples. A relation is a *set* of tuples — no duplicates, no order.

### Constraints

- **Domain constraint** — values must be atomic and from the domain.
- **Key constraints** — a **superkey** identifies tuples; a **candidate key** is a minimal superkey; one is chosen as **primary key**.
- **Entity integrity** — the primary key cannot be NULL.
- **Referential integrity** — a **foreign key** value must match a primary key value in the referenced relation, or be NULL.

### Update operations and violations

**Insert** can violate domain, key, entity or referential integrity. **Delete** can violate referential integrity — handled by **restrict (reject)**, **cascade**, or **set null / set default**. **Update** can violate any of them depending on the attribute. A **transaction** groups operations so the database moves from one consistent state to another.

### Relational algebra

| Operation | Symbol | Meaning |
|---|---|---|
| Select | σ | rows that satisfy a condition |
| Project | π | chosen columns (duplicates removed) |
| Rename | ρ | rename relation/attributes |
| Union, intersection, difference | ∪ ∩ − | need **union-compatible** relations |
| Cartesian product | × | every combination of tuples |
| Join | ⋈ | product followed by a selection; **equijoin**, **natural join** (written R \* S in Elmasri–Navathe, R ⋈ S elsewhere), **theta join** |
| Division | ÷ | "for all" queries |

Additional operations: **aggregate functions and grouping** (ℱ — SUM, AVG, COUNT, MIN, MAX), **outer joins** (left, right, full — keep unmatched tuples with NULLs), and **outer union**.

Example — names of employees in department 5:
π Fname, Lname (σ Dno = 5 (EMPLOYEE))

### ER-to-relational mapping

1. **Regular entity** → a relation with its simple attributes; pick a primary key.
2. **Weak entity** → a relation including the owner's primary key; key = owner key + partial key.
3. **1:1 relationship** → foreign key in one side (prefer the total-participation side).
4. **1:N relationship** → foreign key on the **N** side.
5. **M:N relationship** → a new relation with both primary keys as a composite key, plus relationship attributes.
6. **Multivalued attribute** → a new relation (attribute + owner key).
7. **n-ary relationship** → a new relation with all participating keys.

## Module 3 — Normalisation and SQL basics

> **In short:** **normalisation** splits badly designed tables to remove redundancy and update anomalies, using **functional dependencies** (1NF, 2NF, 3NF, BCNF). **SQL** creates tables and queries them with SELECT … FROM … WHERE.

```flow
1NF: atomic values -> 2NF: no partial dependency -> 3NF: no transitive dependency -> BCNF: every determinant is a key
```

### Informal design guidelines

Give each relation clear semantics; avoid **redundancy** and the **update anomalies** it causes (**insertion, deletion and modification anomalies**); avoid many NULLs; avoid **spurious tuples** (design so joins are **lossless**).

### Functional dependencies

X → Y means any two tuples that agree on X agree on Y. **Armstrong's axioms:** reflexivity, augmentation, transitivity (plus derived rules union, decomposition, pseudotransitivity). The **closure** X⁺ is every attribute determined by X; if X⁺ contains all attributes, X is a superkey.

### Normal forms

- **1NF** — atomic values only; no repeating groups or multivalued attributes.
- **2NF** — 1NF and no **partial dependency** (no non-prime attribute depends on part of a composite key).
- **3NF** — 2NF and no **transitive dependency** of a non-prime attribute on a key. Formally, for every FD X → A: X is a superkey **or** A is prime.
- **BCNF** — for every FD X → A, X is a superkey. Stricter than 3NF; a BCNF decomposition is lossless but may not preserve all dependencies.
- **4NF** — no non-trivial **multivalued dependency** X →→ Y unless X is a superkey.
- **5NF** — no non-trivial **join dependency** except those implied by keys.

To normalise: find the candidate keys, list the FDs, and decompose at each violating FD X → Y into

- **R₁ = X ∪ Y** and **R₂ = R − (Y − X)** (everything except Y, but **keep X**).

This split is always **lossless**: R₁ ∩ R₂ ⊇ X, and X → Y means X is a key of R₁ (the lossless-join test: R₁ ∩ R₂ → R₁ or R₁ ∩ R₂ → R₂).

Example: R(**StudentID**, Course, Dept, HOD) with Dept → HOD violates 3NF (transitive). Split on Dept → HOD: R₁(Dept, HOD) and R₂(StudentID, Course, Dept). Dept stays in R₂ so the two can be joined back.

A **BCNF** decomposition is always lossless but may **lose dependency preservation**: some FD may no longer fit inside any single table. 3NF synthesis can always keep both.

### SQL basics

**Data definition:** `CREATE TABLE`, data types (`INT`, `DECIMAL(p,s)`, `VARCHAR(n)`, `CHAR(n)`, `DATE`), constraints `PRIMARY KEY`, `UNIQUE`, `NOT NULL`, `CHECK`, `DEFAULT`, `FOREIGN KEY … REFERENCES … ON DELETE CASCADE`. Schema changes: `ALTER TABLE … ADD/DROP COLUMN`, `DROP TABLE … CASCADE`.

**Retrieval:**

```sql
SELECT   d.Dname, COUNT(*) AS staff, AVG(e.Salary)
FROM     EMPLOYEE e JOIN DEPARTMENT d ON e.Dno = d.Dnumber
WHERE    e.Salary > 30000
GROUP BY d.Dname
HAVING   COUNT(*) > 2
ORDER BY staff DESC;
```

`WHERE` filters rows before grouping; `HAVING` filters groups. Also `DISTINCT`, `LIKE` with `%` and `_`, `BETWEEN`, `IN`, `IS NULL`, and set operations `UNION`, `INTERSECT`, `EXCEPT`.

**Modification:** `INSERT INTO … VALUES (…)`, `DELETE FROM … WHERE …`, `UPDATE … SET … WHERE …`.

## Module 4 — Advanced SQL and transactions

> **In short:** advanced SQL adds nested queries, joins, aggregates, views, triggers and assertions. A **transaction** is a unit of work that must be **ACID**: atomic, consistent, isolated and durable.

```flow
Active -> Partially committed -> Committed
Active -> Failed -> Aborted (rolled back)
```

### Complex retrieval

- **Nested queries** with `IN`, `= ANY`, `> ALL`; **correlated** subqueries refer to the outer query and run once per outer row.
- `EXISTS` / `NOT EXISTS` — true if the subquery returns any rows; `NOT EXISTS` expresses "for all" (division).
- **Joined tables** — `JOIN … ON`, `NATURAL JOIN`, `LEFT/RIGHT/FULL OUTER JOIN`.
- NULL uses **three-valued logic** (TRUE, FALSE, UNKNOWN); compare with `IS NULL`, never `= NULL`. Aggregates ignore NULLs except `COUNT(*)`.

### Assertions, triggers and views

- `CREATE ASSERTION name CHECK (NOT EXISTS (…))` — a constraint over several tables. It is in the SQL standard (and in the textbook), but most real DBMSs (MySQL, PostgreSQL, Oracle, SQL Server) do not support it; in practice the same rule is enforced with triggers.
- **Trigger (ECA rule):** an **event** (INSERT/UPDATE/DELETE), a **condition**, and an **action**, e.g. log a salary change or reject an invalid update.
- **View** — a virtual table defined by a query (`CREATE VIEW … AS SELECT …`). Used for security and simpler queries; updatable only when it maps unambiguously to one base table (no aggregates/DISTINCT/joins in most systems). Views are kept current by **query modification** or **materialisation**.

### Transaction processing

A **transaction** is a logical unit of work (read/write operations ending in **commit** or **abort**). Concurrent execution without control causes the **lost update**, **dirty read (temporary update)**, **incorrect summary** and **unrepeatable read** problems.

States: **active → partially committed → committed**, or **failed → aborted**. The **system log** records each write so the recovery manager can **undo** or **redo** it.

**ACID properties:** **Atomicity** (all or nothing), **Consistency** (preserves constraints), **Isolation** (as if alone), **Durability** (committed changes survive failures).

### Schedules

A **schedule** interleaves operations of several transactions.

- **Recoverable:** a transaction commits only after every transaction it read from has committed. **Cascadeless:** reads only committed data. **Strict:** no read or write of an item until the last writer commits or aborts.
- **Serial** schedules are always correct. A schedule is **conflict serialisable** if it is conflict-equivalent to a serial schedule — check with a **precedence (serialisation) graph**: draw Tᵢ → Tⱼ for each conflicting pair (same item, at least one write, Tᵢ first); **no cycle** means serialisable, and a topological order gives the equivalent serial schedule. **View serialisability** is weaker but costly to test.

SQL support: `SET TRANSACTION` with four isolation levels. The SQL standard defines them by which problems they allow:

| Isolation level | Dirty read | Non-repeatable read | Phantom |
|---|---|---|---|
| READ UNCOMMITTED | possible | possible | possible |
| READ COMMITTED | prevented | possible | possible |
| REPEATABLE READ | prevented | prevented | possible |
| SERIALIZABLE | prevented | prevented | prevented |

Real engines may prevent more than the standard requires (for example with multiversion concurrency control), so check the specific DBMS.

## Module 5 — Concurrency control and NoSQL

> **In short:** **concurrency control** lets many transactions run together without corrupting data, using **two-phase locking** or timestamps. **NoSQL** databases (key-value, document, column, graph) trade some guarantees for scale and flexible schemas.

```flow
Growing phase: acquire locks, release none -> Lock point -> Shrinking phase: release locks, acquire none
```

### Two-phase locking

Locks: **shared (read)** and **exclusive (write)**. Under **2PL** every transaction has a **growing phase** (acquire, no release) then a **shrinking phase** (release, no acquire); this guarantees conflict serialisability.

- **Strict 2PL** holds exclusive locks until commit/abort (gives strict, recoverable schedules); **rigorous 2PL** holds all locks until the end.
- 2PL can **deadlock**. **Prevention** with timestamps: **wait-die** (an older transaction waits; a younger one dies) and **wound-wait** (an older one wounds/aborts the younger; a younger one waits). **Detection** uses a **wait-for graph** and aborts a victim. **Timeouts** are a simple alternative. Watch for **starvation**.

### Timestamp ordering

Each transaction gets a timestamp TS(T); each item keeps **read_TS** and **write_TS**. A read or write that would violate timestamp order aborts the transaction (which restarts with a new timestamp). **Thomas's write rule** ignores an obsolete write instead of aborting. No deadlocks, but possible cascading rollbacks unless made strict.

### Multiversion and validation techniques

**Multiversion** concurrency control keeps old versions so reads never wait — **MVTO** (timestamp-based) and **multiversion 2PL with certify locks**. **Validation (optimistic)** control lets a transaction run freely through **read**, **validation** and **write** phases, and checks for conflicts only at validation — good when conflicts are rare.

### Granularity and multiple-granularity locking

Lockable items range from a field to a record, block, file or the whole database. Coarse granularity means little overhead but poor concurrency; fine granularity the reverse. **Multiple granularity locking** uses **intention locks** — **IS**, **IX**, **SIX** — on ancestors before locking a node, following a compatibility matrix, so a transaction can lock a whole file or one record as needed.

### NoSQL and big-data storage

NoSQL systems trade some consistency for scale and availability on distributed clusters; they are often **schema-less** and replicate and shard data.

The **CAP theorem:** a distributed system cannot guarantee **Consistency**, **Availability** and **Partition tolerance** all at once; when a network partition happens, it must give up either C or A until the partition heals. Many NoSQL systems choose availability with **eventual consistency**, but not all: some favour consistency, and several let you choose per operation. When there is no partition, a system can offer both C and A.

- **Document stores** (**MongoDB**) — JSON/BSON documents in collections; flexible schema; queries on fields; replication and sharding.
- **Key-value stores** (DynamoDB, Redis, Voldemort) — fast lookup by key.
- **Column-based / wide-column stores** (HBase, Cassandra, Bigtable) — rows with column families, versioned cells.
- **Graph databases** (**Neo4j**) — nodes and relationships with properties, queried with **Cypher**, e.g. `MATCH (e:Employee)-[:WORKS_FOR]->(d:Department) RETURN e, d`.

## Exam tips

- ER diagrams: use the standard notation (double rectangle for weak entities, double line for total participation, 1/N/M labels) and write the cardinality on every relationship.
- Normalisation questions: list the FDs and keys first, then name the violated normal form before decomposing.
- For serialisability, draw the precedence graph and state "cycle → not serialisable" or give the serial order.
