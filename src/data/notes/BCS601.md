## Module 1 — Distributed system models and enabling technologies

> **In short:** computing has moved from single machines to **distributed systems**: many computers on a network working together. **Clusters**, **grids**, **peer-to-peer (P2P)** networks and **clouds** are different ways to organise them. Multicore chips, virtualisation, fast networks and cheap storage are the technologies that made large-scale cloud computing possible.

```flow
Centralised computing -> Parallel computing -> Distributed computing -> Cluster and grid computing -> Cloud computing
```

### Scalable computing over the Internet

- **High-performance computing (HPC):** focuses on raw speed (FLOPS) for scientific jobs.
- **High-throughput computing (HTC):** focuses on completing many tasks per unit time, for example serving millions of web searches. Cloud computing is mainly HTC.
- **Computing paradigms:**
  - **Centralised:** all resources in one system.
  - **Parallel:** processors work at the same time, sharing memory or passing messages.
  - **Distributed:** autonomous computers with their own memory, communicating over a network.
  - **Cloud:** a pool of virtualised resources, centralised or distributed, delivered as a service over the Internet.
- **Design objectives** of these systems: **efficiency**, **dependability** (reliability and self-management), **adaptation** in the programming model (scale to billions of requests), and **flexibility** in deployment.

**Degrees of parallelism:** bit-level → instruction-level (ILP) → data-level (DLP, SIMD) → task-level (TLP) → job-level.

**The Internet of Things (IoT)** connects everyday objects (sensors, RFID tags, devices) to the Internet; **cyber-physical systems (CPS)** combine computation with physical processes. Both generate huge amounts of data that clouds process.

### Technologies for network-based systems

- **Multicore CPUs and multithreading:** many cores per chip; parallel workloads.
- **GPU computing:** graphics processors with thousands of simple cores, used for data-parallel jobs (machine learning, simulations).
- **Memory, storage and wide-area networking:** cheaper, larger disks and flash; faster Ethernet and wide-area links.
- **Virtual machines and virtualisation middleware:**
  - A **virtual machine (VM)** is a software computer running on a physical host.
  - A **virtual machine monitor (VMM, hypervisor)** creates and manages VMs.
  - VM operations: **multiplex** (several VMs on one host), **suspend**, **provision** (resume on any host) and **live migrate** (move a running VM to another host).
- **Data-centre virtualisation:** low-cost commodity servers, virtualised and managed together, give the economies of scale clouds rely on.

### System models for distributed and cloud computing

| System | Architecture | Control | Main use |
|---|---|---|---|
| **Cluster** | Interconnected computers (nodes) on a fast LAN, used as one machine | Centralised, managed as a single system | HPC, servers, databases |
| **Grid** | Clusters and resources at many sites joined over the Internet | Distributed, across organisations | Shared scientific computing |
| **P2P network** | Peers that are both client and server, joined by an overlay network | Fully decentralised, self-organising | File sharing, content distribution |
| **Cloud** | Virtualised resources in data centres | Centrally managed by the provider | On-demand services over the Internet |

- **Clusters** aim for a **single-system image (SSI)**: users see one machine.
- **P2P overlay networks** are either **unstructured** (random links, flooding search) or **structured** (fixed rules, such as distributed hash tables).
- **Cloud computing** provides **on-demand**, **elastic**, **pay-per-use** access to virtualised resources.

### Software environments for distributed systems and clouds

- **Service-oriented architecture (SOA):** a system is built from loosely coupled **services** that communicate through standard interfaces. Implemented with **web services** (SOAP, WSDL) or **REST** (resources accessed with HTTP methods).
- **Trends toward distributed operating systems:** distributed OS (for example Amoeba), network OS, and middleware-based systems that manage resources across machines.
- **Parallel and distributed programming models:**
  - **MPI (Message Passing Interface):** processes exchange messages; used on clusters.
  - **MapReduce:** process huge data sets with a map step and a reduce step (Module 5).
  - **Hadoop:** open-source MapReduce with the HDFS file system.
  - **Open Grid Services Architecture (OGSA)** and **Globus** toolkit for grids.

### Performance, security and energy efficiency

**Performance metrics:** CPU speed (MIPS, FLOPS), network bandwidth and latency, throughput, and **system availability**.

- **Scalability dimensions:** **size** (more processors), **software** (OS and library upgrades), **application** (larger problems), **technology** (adapting to new hardware) and **geographic** spread.
- **Amdahl's law (fixed workload):** if a fraction α of the work is sequential, the speedup on n processors is S = 1 / (α + (1 − α)/n). Even with infinite processors, S cannot exceed 1/α.
- **Gustafson's law (scaled workload):** if the problem grows with the machine, scaled speedup S′ = α + (1 − α) n. More processors allow bigger problems.

**Worked example:** with 10% sequential work (α = 0.1) and 10 processors, Amdahl gives S = 1 / (0.1 + 0.9/10) = 1 / 0.19 ≈ 5.26. With unlimited processors the limit is 1/0.1 = 10.

- **Availability** = MTTF / (MTTF + MTTR), where MTTF is the mean time to failure and MTTR the mean time to repair. Avoid **single points of failure** with redundancy.
- **Network threats and data integrity:** denial of service (DoS), viruses and worms, intrusion, data loss. Defences: firewalls, intrusion detection, encryption, authentication and access control.
- **Energy efficiency:** idle servers waste power. Techniques: **dynamic voltage and frequency scaling (DVFS)**, turning off idle servers, VM consolidation, and efficient cooling in data centres.

## Module 2 — Virtual machines and virtualisation

> **In short:** **virtualisation** lets one physical machine run several **virtual machines**, each with its own operating system. It can be done at different levels (hardware, OS, library, application). The **hypervisor** shares the CPU, memory and I/O between VMs. Virtual clusters and live migration let data centres move workloads, balance load and save energy.

```flow
Hardware -> Hypervisor (VMM) -> Virtual machines (guest OS + applications)
```

### Implementation levels of virtualisation

| Level | How it works | Examples |
|---|---|---|
| Instruction set architecture (ISA) | Emulate one CPU's instructions on another | Bochs, QEMU (emulation) |
| Hardware abstraction (bare-metal) | Hypervisor virtualises the hardware for full guest OSs | VMware ESX, Xen, KVM |
| Operating-system level | One OS kernel runs many isolated **containers** | Docker, LXC, OpenVZ |
| Library support (user-level API) | Intercept library calls to emulate another environment | WINE (Windows apps on Linux) |
| User application level | A process-level VM runs programs | Java Virtual Machine, .NET CLR |

**Relative merits:** higher levels (OS, library, application) have less overhead but less isolation and flexibility; hardware-level virtualisation gives strong isolation and runs any OS, at a higher cost.

**Requirements of a VMM (Popek and Goldberg):** it gives an environment **essentially identical** to the original machine, programs run with only **minor speed loss**, and the VMM has **complete control** of resources.

**OS-level virtualisation (containers):** share one kernel, start quickly, use little memory, but all containers must use the same OS kernel family.

### Virtualisation structures, tools and mechanisms

Where the virtualisation layer sits:

- **Hypervisor (bare-metal) architecture:** the hypervisor runs directly on hardware.
  - **Micro-kernel hypervisor** (such as **Xen**): only basic functions (memory, CPU scheduling) in the hypervisor; device drivers in a privileged domain.
  - **Monolithic hypervisor** (such as **VMware ESX**): drivers and other functions inside the hypervisor.
- **Xen architecture:** the hypervisor plus **Domain 0** (a privileged VM that manages the others and holds the drivers) and **Domain U** guest VMs.
- **Full virtualisation:** the guest OS is unmodified; non-critical instructions run directly on hardware, and **critical (sensitive) instructions** are trapped and emulated by the VMM, using **binary translation** (VMware).
- **Host-based virtualisation:** a VMM runs on top of a normal host OS (such as VMware Workstation). Easy to install but slower.
- **Para-virtualisation:** the guest OS is **modified** to call the hypervisor directly (**hypercalls**) instead of using sensitive instructions. Faster, but the OS must be changed (Xen, KVM's para-virtual drivers).

### Virtualisation of CPU, memory and I/O devices

- **Hardware support:** modern CPUs add virtualisation extensions (Intel VT-x, AMD-V) with an extra privilege mode, so the VMM can trap sensitive instructions efficiently.
- **CPU virtualisation:** instructions are **privileged**, **control-sensitive** or **behaviour-sensitive**. A CPU is virtualisable if all sensitive instructions are privileged (so they can be trapped).
- **Memory virtualisation:** two-stage mapping, **virtual → guest physical → host (machine) physical**. The VMM keeps **shadow page tables**, or the hardware uses **nested (extended) page tables** to do both steps.
- **I/O virtualisation:** three approaches:
  - **Full device emulation:** the VMM emulates a real device (slow).
  - **Para-virtualised I/O:** split drivers, a front-end in the guest and a back-end in the privileged domain (faster).
  - **Direct I/O:** the VM accesses the device directly (fastest, harder to share). **SR-IOV** lets one device appear as several.
- **Virtualisation in multicore processors:** physical cores can be shown as virtual cores, and the VMM schedules virtual CPUs on physical cores.

### Virtual clusters and resource management

A **virtual cluster** is built from VMs on many physical machines, joined by a virtual network.

- VMs can be **added or removed** dynamically; a virtual cluster's size can change.
- Many virtual clusters can share the same physical machines, isolated from each other.
- **Fast deployment:** use templates and pre-built images to start many VMs quickly.

**Live migration of VMs** (moving a running VM to another host with almost no downtime):

```flow
Pre-migration (choose target host) -> Reservation (reserve resources) -> Iterative pre-copy (copy memory, then copy dirty pages again) -> Stop-and-copy (pause VM, copy last pages and CPU state) -> Commitment -> Activation on new host
```

Downtime is only the short **stop-and-copy** phase. Migration is used for load balancing, maintenance and energy saving.

**Migration of memory, files and network:** memory is copied as above; the file system is usually shared (network storage) so files need not move; the VM keeps its IP address and the network is told the new location.

### Virtualisation for data-centre automation

- **Server consolidation:** run many under-used servers' workloads as VMs on fewer physical machines, raising utilisation and cutting power and space.
- **Virtual storage management:** storage is virtualised and managed across the data centre (VM images, virtual disks).
- **Cloud OS for virtualised data centres:** systems such as Eucalyptus, OpenNebula and vSphere manage VMs, storage and networks across the whole data centre.
- **Trust management in virtualised data centres:** the VMM is a security boundary; **VM-based intrusion detection** can watch VMs from outside.

## Module 3 — Cloud platform architecture

> **In short:** clouds are delivered in **service models**: **IaaS** (virtual machines and storage), **PaaS** (a platform to run your code) and **SaaS** (finished applications). They are deployed as **public**, **private**, **hybrid** or **community** clouds. Behind them are huge **data centres** with special network designs. Major public platforms are **Google App Engine**, **Amazon Web Services** and **Microsoft Azure**.

```flow
SaaS (applications: Gmail, Salesforce) -> PaaS (platforms: Google App Engine) -> IaaS (VMs and storage: Amazon EC2, S3) -> Data-centre hardware
```

### Cloud computing and service models

**Deployment models:**

- **Public cloud:** owned by a provider, shared by many customers over the Internet (AWS, Azure, Google Cloud).
- **Private cloud:** run for one organisation, on its premises or hosted.
- **Hybrid cloud:** a mix; for example, sensitive work in a private cloud and peaks sent to a public cloud (**cloud bursting**).
- **Community cloud:** shared by organisations with common concerns.

**Service models:**

| Model | User controls | Provider manages | Examples |
|---|---|---|---|
| **IaaS** (Infrastructure as a Service) | OS, middleware, applications, data | Servers, storage, network, virtualisation | Amazon EC2, S3; Azure VMs |
| **PaaS** (Platform as a Service) | Applications and data | Runtime, OS, servers, scaling | Google App Engine, Azure App Service, Heroku |
| **SaaS** (Software as a Service) | Only use and settings | The whole application stack | Gmail, Salesforce, Microsoft 365 |

**Cloud benefits:** no up-front investment, pay-per-use, **elasticity** (scale up and down quickly), high availability, and access from anywhere. **Concerns:** security and privacy, vendor lock-in, network dependence, and compliance.

### Data-centre design and interconnection networks

- **Warehouse-scale data centres** hold hundreds of thousands of servers in racks.
- **Cooling** is a major cost; designs use hot and cold aisles and raised floors.
- **Cost model:** spending is mostly on servers, power and cooling. Commodity hardware and automation keep it low.
- **Data-centre interconnection networks** must support all-to-all traffic, scale to many servers, be fault-tolerant and cheap:
  - **Fat-tree** networks: switches arranged in layers (core, aggregation, edge), giving many equal paths between servers.
  - **Server-centric** designs (such as **BCube**) where servers also forward traffic, used in modular container data centres.
- **Modular data centres in containers:** pre-built containers of servers and cooling that can be shipped and plugged in.

### Architectural design of compute and storage clouds

**Generic cloud architecture:** a **cloud platform** sits on virtualised infrastructure and offers services through a portal. It includes resource provisioning, monitoring, billing, and security.

**Design objectives:** shift computing from desktops to data centres, use service provisioning and cloud economics, scale performance, preserve data privacy, and give high quality of service (QoS).

**Layered cloud architecture:**

```flow
Infrastructure layer (compute, storage, network resources) -> Platform layer (runtime, middleware) -> Application layer (SaaS applications)
```

- **Market-oriented cloud architecture:** a **service-level agreement (SLA)** sets the quality the customer pays for; a **resource allocator** (SLA manager, pricing, accounting, VM monitor, dispatcher) matches requests with resources.
- **Virtualisation support and disaster recovery:** VMs make it easy to replicate and restore services elsewhere.
- **Architectural challenges:** service availability and data lock-in, data privacy and security, unpredictable performance, distributed storage and bugs at scale, cloud scalability and fast scaling, software licensing.

### Public cloud platforms: GAE, AWS and Azure

**Google App Engine (GAE):** a **PaaS** for web applications.

- Developers upload code (Python, Java, Go and others); Google runs and scales it automatically.
- Uses Google's infrastructure: **Google File System (GFS)**, **Bigtable** (a NoSQL store), **MapReduce**, and **Chubby** (a lock service).
- The **datastore** stores application data; developers don't manage servers.

**Amazon Web Services (AWS):** mainly **IaaS** plus many services.

- **EC2 (Elastic Compute Cloud):** virtual machines (**instances**) of various sizes.
- **S3 (Simple Storage Service):** object storage in **buckets**.
- **EBS (Elastic Block Store):** virtual disks for EC2.
- **SQS** (message queues), **SimpleDB / DynamoDB** (NoSQL), **RDS** (relational databases), **CloudWatch** (monitoring), **Elastic Load Balancing** and **Auto Scaling**.

**Microsoft Azure:** a cloud platform with IaaS and PaaS.

- **Compute** roles (web roles and worker roles in the original design), **storage** (blobs, tables, queues), **SQL Azure** (relational database) and the **Azure fabric controller**, which manages resources.

### Inter-cloud resource management

- **Extended cloud computing services:** clouds stacked as layers: hardware as a service, network as a service, data as a service, and so on.
- **Resource provisioning:** decide how many VMs to give each service.
  - **Demand-driven:** add or remove resources based on current load.
  - **Event-driven:** plan for expected events (such as a festival sale).
  - **Popularity-driven:** based on Internet traffic for that service.
- **Virtual machine creation and management**, and **global exchange of cloud resources**: a cloud **federation** lets providers share resources through brokers and exchanges, so a user's work can run on whichever cloud is best.

## Module 4 — Cloud security and trust management

> **In short:** moving data and computation to someone else's servers raises **security**, **privacy** and **trust** concerns. Risks include data breaches, insecure interfaces, malicious insiders and attacks between VMs on the same host. Defences combine **encryption**, **access control**, **secure hypervisors**, **intrusion detection** and **reputation systems** to protect data centres.

```flow
Identify assets and risks -> Encrypt data (at rest and in transit) -> Control access (authentication, authorisation) -> Monitor (intrusion and anomaly detection) -> Respond and recover
```

### Top concerns for cloud users

- **Loss of control** over data stored on the provider's servers.
- **Multi-tenancy:** many customers share the same hardware.
- **Data location** and legal jurisdiction (compliance).
- **Availability** of the service, and **vendor lock-in**.
- **Insider threats** at the provider.

The user must trust the provider's security, so **service-level agreements** should cover security, data handling and audits.

### Cloud security risks

Risks fall into three groups:

- **Traditional security threats:** DDoS attacks, phishing, SQL injection, cross-site scripting; made worse by the cloud's scale.
- **Threats related to system availability:** system failures, power outages, catastrophic events.
- **Threats related to third-party data control:** the provider (or its subcontractors) may misuse, lose or disclose data.

The **Cloud Security Alliance's** list of top threats includes: abuse of cloud services, insecure APIs, malicious insiders, shared-technology vulnerabilities, data loss or leakage, and account or service hijacking.

### Privacy and privacy impact assessment

**Privacy** is the right to control one's personal information. In the cloud, users lose control of where their data is stored and who can see it.

A **privacy impact assessment (PIA)** is a process that:

1. identifies what personal data a system will collect and how it will be used,
2. assesses the privacy risks, and
3. proposes ways to reduce them, before the system is deployed.

### Cloud data encryption and security of database services

- Encrypt data **in transit** (TLS) and **at rest** (disk or database encryption).
- **Key management** is the hard part: whoever holds the keys controls the data. Keeping keys with the customer increases control.
- Computing on encrypted data is possible in limited forms (**homomorphic encryption**), but is still slow.
- **Database-as-a-service security:** the provider runs the database, so customers rely on access controls, encryption and auditing; sensitive columns can be encrypted before upload.

### Operating system and VM security

- **OS security:** the OS must enforce access control, protect memory and authenticate users; a compromised OS exposes all its applications.
- **VM security:** the hypervisor isolates VMs, but:
  - a **compromised hypervisor** exposes every VM on the host,
  - **VM escape** attacks break out of a VM into the host,
  - **side-channel** attacks may leak data between VMs sharing hardware.
- **Security risks posed by shared images:** public VM images (such as community AMIs) may contain malware, back doors, leftover credentials or unpatched software. Check and harden images before use.
- **Security risks posed by a management OS:** the privileged management VM (such as Xen's Domain 0) has wide power; if it is attacked, all guests are at risk.

### XOAR: breaking the monolithic management VM

**Xoar** is a modified Xen design that splits the large privileged control VM (Domain 0) into many small, single-purpose service VMs.

- Each service VM has only the privileges it needs (**least privilege**).
- Services can be restarted or refreshed regularly to clear any compromise.
- This greatly reduces the **trusted computing base** and limits the damage of one compromised component.

### A trusted hypervisor

A trusted, minimal hypervisor protects guest data even from a compromised guest OS or administrator. The textbook discusses **Terra**, a trusted virtual machine monitor that can run both open (general) and closed (sealed, tamper-resistant) VMs, with **attestation** so a remote party can verify what software is running.

### Mobile devices and cloud security

Mobile devices often access cloud services and store credentials, so they add risks: lost or stolen devices, malicious apps, insecure Wi-Fi, and weak authentication. Defences include device encryption, mobile device management (MDM), app vetting and multi-factor authentication.

### Cloud security defence strategies

A layered **defence in depth**:

- **Basic security:** firewalls, intrusion detection, anti-malware, patching.
- **Data protection:** encryption, watermarking, data coloring, backups.
- **Security-aware cloud architecture:** secure hypervisors, VM isolation, protected management, secure data centres.
- **Defence against network attacks:** DDoS detection and mitigation, traffic filtering.
- **Physical and personnel security** at the data centre.

### Distributed intrusion and anomaly detection

- **Intrusion detection systems (IDS):** **host-based (HIDS)** watch one machine; **network-based (NIDS)** watch traffic.
- **Signature-based** detection matches known attack patterns; **anomaly-based** detection flags behaviour that deviates from normal.
- In clouds, IDS can run inside VMs, in the hypervisor (watching VMs from outside, harder to evade) or across the network, and their alerts are combined (**distributed IDS**).
- **DDoS defence:** detect traffic surges early (for example, by watching changes in traffic patterns at routers) and filter attack traffic close to its source.

### Data and software protection techniques

- **Data integrity and privacy:** encryption, hashing (to detect tampering), access control.
- **Data coloring and watermarking:** marks embedded in data or software to trace ownership and detect copying or leaks.
- **Data lock-in:** use standard formats and APIs so data can be moved between providers.

### Reputation-guided protection of data centres

A **reputation system** rates the trustworthiness of providers, sites or peers from their past behaviour and feedback.

- **Centralised** systems keep ratings in one place; **distributed** (P2P) systems spread them.
- Cloud reputation can combine data from many sites to identify **trustworthy providers** and isolate **malicious** ones.
- It guides decisions such as which data centre or service to use, and helps defend against attacks like collusion and false feedback.

## Module 5 — Cloud programming and software environments

> **In short:** cloud platforms need programming models that spread work across thousands of machines. **MapReduce** splits a big job into a **map** step (process pieces in parallel) and a **reduce** step (combine results); **Hadoop** is its open-source version. Each provider (Google, Amazon, Microsoft) offers its own tools, and newer environments (Eucalyptus, OpenNebula, Aneka) help build private and hybrid clouds.

```flow
Input data -> Split into chunks -> Map (emit key, value pairs) -> Shuffle and sort by key -> Reduce (combine values per key) -> Output
```

### Features of cloud and grid platforms

- **Capabilities:** physical or virtual computing platform, massive data storage, high availability, monitoring, accounting and billing, and support for many programming models.
- **Traditional features** common to clouds and grids: workflow, data transport, security and privacy, availability.
- **Data features and databases:** program libraries, blobs and drives, DPFS (data-parallel file systems), SQL and table storage, queuing services.
- **Programming and runtime support:** worker and web roles, MapReduce, scripting languages, the publish–subscribe model, and fault tolerance.

### Parallel and distributed computing paradigms

**Motivations for parallel and distributed programming models:** they hide the hard parts from the programmer: **partitioning** the computation and data, **mapping** them to machines, **synchronisation**, **communication** and **scheduling**.

**MapReduce:**

- The user writes two functions:
  - **Map:** (key₁, value₁) → list of (key₂, value₂)
  - **Reduce:** (key₂, list of value₂) → list of value₃
- The runtime handles splitting, scheduling, moving data, and **fault tolerance** (failed tasks are re-run on other machines).

**Example: word count**

- **Map:** for each word w in a line, emit (w, 1).
- **Shuffle:** group all pairs by word: ("cloud", [1, 1, 1]).
- **Reduce:** sum the list: ("cloud", 3).

**MapReduce execution steps:** split the input → start the master and workers → map tasks read splits and write intermediate pairs to local disk → the master tells reducers where the data is → reducers read and sort it → reduce tasks write the final output.

**Twister and iterative MapReduce:** many algorithms (k-means, PageRank) repeat MapReduce steps; Twister keeps data in memory between iterations to make this efficient.

**Hadoop:**

- **HDFS (Hadoop Distributed File System):** stores files in large **blocks** (for example 64 or 128 MB), each **replicated** (default 3 copies) on different nodes. A **NameNode** holds the metadata; **DataNodes** hold the blocks.
- **MapReduce engine:** a **JobTracker** schedules jobs and **TaskTrackers** on each node run map and reduce tasks (classic Hadoop 1; later versions use **YARN** for resource management).
- **Data locality:** tasks are scheduled on the nodes that already hold the data, to avoid moving it.

**Dryad and DryadLINQ** (Microsoft): express a job as a directed acyclic graph (DAG) of operations; **Sawzall** and **Pig Latin** are high-level languages for writing data-parallel jobs.

### Programming support for Google App Engine

- **Programming GAE:** applications are written in supported languages and use GAE's APIs.
- **Google File System (GFS):** stores very large files split into **chunks** (64 MB), replicated across **chunk servers**, with one **master** holding metadata. Designed for large sequential reads and appends, on cheap hardware where failures are normal.
- **Bigtable:** a distributed storage system for structured data: a sparse, sorted, multi-dimensional map indexed by **(row key, column key, timestamp)**. Tables are split into **tablets** served by tablet servers.
- **Chubby:** a distributed **lock service** that keeps small files and coordinates the system (for example, electing a master).

### Programming on Amazon AWS and Microsoft Azure

**Amazon:**

- **EC2:** choose an **AMI** (machine image), an instance type and a region; launch, connect, and stop instances when done. Pay per hour or second.
- **S3:** store objects in buckets, accessed by REST or SOAP; objects can be up to terabytes in size.
- **EBS** volumes attach to instances as disks; **SimpleDB / DynamoDB** store structured data without a fixed schema; **SQS** passes messages between components to decouple them.
- **Amazon Elastic MapReduce** runs Hadoop jobs on EC2.

**Microsoft Azure:**

- **Roles:** **web roles** run web front ends; **worker roles** run background processing. Roles communicate through **queues**.
- **Azure storage:** **blobs** (large binary objects), **tables** (structured, non-relational) and **queues** (messages).
- **SQL Azure** (now Azure SQL Database) for relational data.

### Emerging cloud software environments

- **Open-source Eucalyptus:** builds private clouds compatible with the AWS interfaces (EC2 and S3 APIs).
- **Nimbus:** an open-source toolkit for turning a cluster into an IaaS cloud for science.
- **OpenNebula:** an open-source toolkit for managing virtualised data centres and hybrid clouds.
- **Sector/Sphere:** a distributed storage (Sector) and processing (Sphere) system for large data sets across wide areas.
- **OpenStack:** an open-source IaaS platform with compute (Nova), object storage (Swift) and other services.
- **Manjrasoft Aneka:** a .NET-based platform for building and deploying cloud applications, supporting several programming models (task, thread and MapReduce).

## Exam tips

- Draw and explain the **service models (IaaS, PaaS, SaaS)** with examples and a comparison table; and the **deployment models**. Asked almost every year.
- Compare **cluster, grid, P2P and cloud**; and **full virtualisation vs para-virtualisation**, with the **Xen architecture** diagram.
- Solve an **Amdahl's law** speedup and an **availability (MTTF, MTTR)** numerical.
- Draw the **live migration** steps and the **MapReduce** data flow with a **word count** example.
- Know the main services of **AWS** (EC2, S3, EBS, SQS), **GAE** (GFS, Bigtable, Chubby) and **Azure** (roles, blobs, tables, queues).
- For security, list the **top cloud threats** and explain **defence strategies**, **XOAR** and **intrusion detection** in the cloud.
