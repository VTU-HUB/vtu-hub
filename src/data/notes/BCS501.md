## Module 1 — Software, software engineering and process models

> **In short:** software engineering is a disciplined way to build software that works, on time and within budget. Every project follows a **process**: communication, planning, modelling, construction and deployment. **Process models** (waterfall, incremental, spiral, unified) arrange these activities in different orders.

```flow
Communication -> Planning -> Modelling -> Construction -> Deployment
```

### The nature of software

**Software** is programs plus the documents and data that make them usable. It differs from hardware:

- It is **developed (engineered)**, not manufactured.
- It does not **wear out**, but it **deteriorates** because every change can add new defects.
- Most software is still custom-built, although reuse of components keeps growing.

**Application domains:** system software, application software, engineering/scientific software, embedded software, product-line software, web and mobile apps, and AI software.

**Legacy software** is old software that is still critical to a business. It must be adapted, enhanced or re-engineered rather than thrown away.

### The unique nature of WebApps

Web applications have extra properties:

- **Network intensive** and **concurrent** (many users at once).
- **Unpredictable load**: the number of users can jump from 100 to 100,000.
- **Performance and availability** matter: users leave slow sites; people expect 24/7 access.
- **Data driven**, **content sensitive**, **continuously evolving**, with **immediacy** (short time to market), **security** and **aesthetics** as major concerns.

### Software engineering

IEEE defines software engineering as the application of a **systematic, disciplined, quantifiable** approach to the development, operation and maintenance of software.

It is a **layered technology**:

| Layer | Meaning |
|---|---|
| Quality focus | The foundation: everything aims at quality |
| Process | The framework of activities that holds the layers together |
| Methods | The "how to": requirements, design, testing techniques |
| Tools | Automated support for the process and methods (CASE tools) |

### The software process

A **process** is a collection of **activities, actions and tasks** performed to create a work product.

- **Framework activities** (the generic process): communication, planning, modelling, construction, deployment.
- **Umbrella activities** run across the whole project: project tracking and control, risk management, quality assurance, technical reviews, measurement, configuration management, reusability management, and work-product preparation.

### Software engineering practice

Polya's problem-solving steps map onto practice:

1. **Understand the problem** (communication and analysis).
2. **Plan a solution** (modelling and design).
3. **Carry out the plan** (code generation).
4. **Examine the result** (testing and quality assurance).

**Hooker's seven principles:** the reason it all exists (provide value to users); keep it simple; maintain the vision; what you produce, others will consume; be open to the future; plan ahead for reuse; think.

### Software myths

| Type | Myth | Reality |
|---|---|---|
| Management | "We have a book of standards, so we're fine." | Nobody may use the book, and it may be outdated. |
| Management | "If we are behind, add more programmers." | Adding people to a late project makes it later (Brooks's law). |
| Customer | "A general statement of objectives is enough to start coding." | Vague requirements cause failure. |
| Customer | "Requirements change, but change is easy because software is flexible." | Change costs grow sharply the later it happens. |
| Practitioner | "Once the program works, our job is done." | 60–80% of the effort comes after delivery. |
| Practitioner | "The only deliverable is the working program." | Models, documents and plans are part of the product. |

### A generic process model and process assessment

The **process flow** describes how the framework activities are arranged:

- **Linear**: each activity once, in order.
- **Iterative**: repeat one or more activities before moving on.
- **Evolutionary**: go around all activities in circles, each circle producing a more complete version.
- **Parallel**: some activities run at the same time.

**Process assessment** checks that a process meets basic criteria. Examples: **SCAMPI** (from CMMI), **CBA IPI**, **SPICE (ISO/IEC 15504)** and **ISO 9001:2000** for software.

### Prescriptive process models

- **Waterfall model:** a linear sequence, communication → planning → modelling → construction → deployment.
  - Good when requirements are fixed and well understood.
  - Problems: real projects rarely follow a straight line; the customer must state all requirements up front; a working version arrives only at the end.
- **V-model:** a variant of waterfall that pairs each development step with a matching test step (requirements ↔ acceptance testing, design ↔ integration testing, code ↔ unit testing).
- **Incremental model:** delivers the software in **increments**, each a working part. The first increment is the **core product**. Useful when staff are limited or an early version is needed.
- **Evolutionary models:**
  - **Prototyping:** build a quick prototype to clarify unclear requirements, then evaluate it with the customer and refine. Risk: the customer may treat the throwaway prototype as the product.
  - **Spiral model (Boehm):** each loop of the spiral goes through planning, **risk analysis**, engineering and evaluation. **Risk-driven**, suitable for large, high-risk projects.
- **Concurrent model:** activities exist at the same time in different **states** (none, under development, awaiting changes, under review, done). Events trigger the move between states.

### Specialised process models

- **Component-based development:** build from existing **COTS** (commercial off-the-shelf) components: research components, integrate them, test.
- **Formal methods model:** specify the software mathematically, so errors can be found by proof. Costly; used for safety-critical systems.
- **Aspect-oriented software development:** handles **cross-cutting concerns** (security, logging) that affect many parts of the system.

### The Unified Process

A **use-case driven, architecture-centric, iterative and incremental** process, closely tied to UML. Phases:

1. **Inception:** business case, main use cases, rough architecture.
2. **Elaboration:** refine use cases, build the architecture baseline.
3. **Construction:** develop and test the components.
4. **Transition:** deliver to users (beta testing, feedback).
5. **Production:** monitor use, support and fix defects.

### Personal and team process models

- **Personal Software Process (PSP):** an individual engineer measures their own work (time, defects) to improve. Activities: planning, high-level design, design review, development, postmortem.
- **Team Software Process (TSP):** builds self-directed teams of 3–20 engineers that plan and track their work and manage quality. Activities: project launch, high-level design, implementation, integration and test, postmortem.

## Module 2 — Understanding and modelling requirements

> **In short:** before building, find out exactly what the customer needs. **Requirements engineering** draws out, writes down, negotiates and checks requirements. They are then **modelled** with scenarios (use cases), classes, data flows and behaviour diagrams so that everyone understands the same thing.

```flow
Inception -> Elicitation -> Elaboration -> Negotiation -> Specification -> Validation -> Requirements management
```

### Requirements engineering tasks

1. **Inception:** understand the basic problem, the people who want a solution, and the nature of the solution.
2. **Elicitation:** draw out requirements from stakeholders. Problems: unclear **scope**, poor **understanding** by customers, and **volatility** (requirements change).
3. **Elaboration:** refine the information into an analysis model (scenarios, classes, relationships).
4. **Negotiation:** resolve conflicts and rank requirements by priority, cost and risk.
5. **Specification:** write it down: a document, models, use cases or a prototype (an **SRS**).
6. **Validation:** check the requirements for errors, ambiguity, omissions and conflicts, usually by **technical reviews**.
7. **Requirements management:** track requirements and their changes through the project (traceability tables).

### Establishing the groundwork

- Identify the **stakeholders** (anyone who benefits from the system).
- Recognise **multiple viewpoints**: marketing, managers, users and engineers each want different things.
- Work toward **collaboration**.
- Ask the **first questions**: who is behind the request, who will use it, what is the economic benefit?

### Eliciting requirements

- **Collaborative requirements gathering:** a meeting with a facilitator, an agenda and a definition mechanism (whiteboard, chat). Each participant brings a list of objects, services, constraints and performance criteria.
- **Quality function deployment (QFD):** translates customer needs into technical requirements. It sorts requirements into **normal** (stated), **expected** (so basic the customer may not mention them) and **exciting** (beyond expectations).
- **Usage scenarios:** stories of how the system will be used.
- **Work products:** statement of need and feasibility, scope statement, list of stakeholders, technical environment, list of requirements, usage scenarios, prototypes.

### Developing use cases

A **use case** describes how an **actor** (a person or device outside the system) uses the system to reach a goal. A use-case template covers:

- primary actor, goal in context, preconditions, trigger
- **scenario** (the main steps)
- **exceptions** (what can go wrong), priority, frequency of use, open issues

### Building the requirements (analysis) model

The model has four kinds of elements:

| Element | What it shows | Examples |
|---|---|---|
| Scenario-based | The system from the user's point of view | Use cases, activity diagrams |
| Class-based | Objects, attributes and operations | Class diagrams, CRC cards |
| Behavioural | How the system reacts to events | State diagrams, sequence diagrams |
| Flow-oriented | How data is transformed | Data flow diagrams (DFDs) |

**Analysis patterns** capture solutions that recur across applications in a domain.

### Negotiating and validating requirements

**Negotiation (win-win):** identify the key stakeholders, find their "win conditions", and negotiate until each side has a set of wins it can live with.

**Validation questions:** Is each requirement consistent with the objectives? Is it at the right level of abstraction? Is it needed? Is it bounded and unambiguous? Does it have a source? Does it conflict with another? Is it achievable and testable?

### Scenario-based modelling

- **Use-case diagrams** show actors and use cases.
- **Activity diagrams** (UML) show the flow of a scenario, with decisions (diamonds) and parallel paths.
- **Swimlane diagrams** are activity diagrams split into lanes, one per actor or class, showing who does what.

### Data modelling concepts

- **Data object:** a thing with several properties (a person, a report, an order).
- **Attributes:** name, describe or reference an object.
- **Relationships:** how objects connect, with **cardinality** (one-to-one, one-to-many, many-to-many) and **modality** (0 = optional, 1 = mandatory).
- The model is drawn as an **ERD** (entity-relationship diagram).

### Class-based modelling

- **Identify analysis classes** by underlining nouns in the problem statement. Candidates are external entities, things, events, roles, organisational units, places and structures.
- **Attributes** and **operations** (from the verbs) are added to each class.
- **CRC modelling:** an index card per **C**lass, listing its **R**esponsibilities and **C**ollaborators.
- **Associations and dependencies** link classes; **analysis packages** group related classes.

### Requirement modelling strategies

**Flow-oriented modelling:**

- A **data flow diagram (DFD)** shows how data moves through processes.
- The **level 0 DFD (context diagram)** shows the whole system as one bubble with its external entities.
- Each level refines a bubble into more detail. Data entering and leaving a bubble must balance across levels.
- A **control flow model** and **control specification (CSPEC)** handle event-driven parts; a **process specification (PSPEC)** describes each lowest-level process.

**Behavioural modelling:**

1. Evaluate the use cases to understand the interaction sequence.
2. Identify **events** that drive the interaction.
3. Create a **sequence diagram** for each use case.
4. Build a **state diagram** for the system or each class.
5. Review the model for accuracy and consistency.

## Module 3 — Agile development and principles of practice

> **In short:** **agile** development accepts that requirements change. It delivers working software in small, frequent increments, keeps the team and customer in close contact, and prefers working code over heavy documents. **Extreme Programming (XP)** is the best-known agile method.

```flow
XP: Planning (user stories) -> Design (simple, CRC cards) -> Coding (pair programming, tests first) -> Testing (unit + acceptance) -> Release increment
```

### What is agility?

**Agility** is the ability to respond to change. The **Agile Manifesto** values:

- **Individuals and interactions** over processes and tools
- **Working software** over comprehensive documentation
- **Customer collaboration** over contract negotiation
- **Responding to change** over following a plan

### Agility and the cost of change

In a conventional process, the **cost of a change rises steeply** the later it happens (a change during testing costs far more than one during requirements). A well-run agile process **flattens** this curve, because the software is delivered and tested in small increments and design is kept simple.

### What is an agile process?

An agile process is built on three assumptions:

1. It is hard to predict which requirements will persist and which will change.
2. Design and construction are interleaved, so it is hard to predict how much design is needed before building.
3. Analysis, design, construction and testing are not as predictable as we would like.

So the process must be **adaptable**, and adapt **incrementally**, using customer feedback on each **software increment**.

**The 12 agility principles (summary):** satisfy the customer through early and continuous delivery; welcome changing requirements; deliver working software frequently; business people and developers work together daily; build projects around motivated people; face-to-face conversation; working software is the main measure of progress; sustainable pace; technical excellence and good design; simplicity; self-organising teams; regular reflection and tuning.

**Human factors** an agile team needs: competence, common focus, collaboration, decision-making ability, fuzzy problem-solving ability, mutual trust and respect, and self-organisation.

### Extreme Programming (XP)

**XP values:** communication, simplicity, feedback, courage and respect.

**XP process (four activities):**

1. **Planning:** the customer writes **user stories**, each with a value (priority). The team estimates each story's cost in development weeks. Stories are grouped into a **release**. **Project velocity** (stories completed per release) is used to plan the next one.
2. **Design:** keep it simple (**KIS**). Use **CRC cards**. For a hard problem, build a quick **spike solution** (a design prototype). **Refactoring** improves the internal structure without changing behaviour.
3. **Coding:** write **unit tests before the code** (test-first). **Pair programming**: two people at one workstation, one codes while the other reviews. **Continuous integration** of the pairs' code.
4. **Testing:** unit tests run daily and automatically; **acceptance tests** (customer tests) check the user stories.

**Industrial XP (IXP)** adds: readiness assessment, a project community, project chartering, test-driven management, retrospectives and continuous learning.

### Other agile process models

| Model | Key idea |
|---|---|
| **Adaptive Software Development (ASD)** | Speculation → collaboration → learning cycles |
| **Scrum** | Work in **sprints** (2–4 weeks) from a prioritised **backlog**; daily 15-minute **Scrum meeting** (what did you do, what will you do, what is blocking you); a **Scrum master** removes obstacles; a demo at the end of each sprint |
| **Dynamic Systems Development Method (DSDM)** | Time-boxed; the 80/20 rule (80% of the value comes from 20% of the work); iterative prototyping |
| **Crystal** | A family of methods tuned to team size and project criticality |
| **Feature Driven Development (FDD)** | Plan, design and build by **feature** (a client-valued function deliverable in two weeks or less) |
| **Lean Software Development** | Eliminate waste, build quality in, deliver fast, respect people |
| **Agile Modelling (AM)** | Model with a purpose, travel light, use multiple models, content over representation |
| **Agile Unified Process (AUP)** | "Serial in the large, iterative in the small" |

**Tool set for agile process:** tools that support collaboration and communication (whiteboards, shared workspaces, video), physical team arrangements, and automated testing and integration tools.

### Principles that guide practice

**Software engineering knowledge:** a core of principles stays stable even as technologies change.

**Core principles:**

- **Process principles:** be agile; focus on quality at every step; be ready to adapt; build an effective team; set up communication and coordination; manage change; assess risk; create work products that give value to others.
- **Practice principles:** divide and conquer; use abstraction; strive for consistency; focus on the transfer of information; build software that shows effective modularity; look for patterns; represent the problem and solution from different perspectives; remember that someone will maintain the software.

### Principles for each framework activity

| Activity | Key principles |
|---|---|
| Communication | Listen; prepare before you communicate; someone should facilitate; face-to-face is best; take notes; aim for collaboration; stay focused; draw a picture if something is unclear; move on once agreed; negotiation is not a contest |
| Planning | Understand the scope; involve stakeholders; plans are iterative; estimate from what you know; consider risk; be realistic; adjust granularity; define how to ensure quality; describe how to handle change; track the plan often |
| Modelling | The aim is software, not models; travel light; produce the simplest model that describes the problem; build models that are easy to change; state a purpose for each model; adapt models to the system; build useful, not perfect, models; get feedback early |
| Construction | Coding: understand the problem, choose data structures, keep conditional logic simple, use meaningful names. Testing: tests should trace to requirements, be planned early, follow the Pareto principle, and move from small to large |
| Deployment | Manage customer expectations; assemble and test a complete delivery package; establish support before delivery; give users instructional material; fix bugs before delivery |

## Module 4 — Introduction to project management and project evaluation

> **In short:** a **project** is a planned, one-off piece of work with a goal and limits on time and cost. **Software project management** plans, organises, monitors and controls such projects so they succeed. Before starting, a project is **evaluated**: is it worth it (cost–benefit), and how risky is it?

```flow
Feasibility study -> Planning -> Project execution -> Monitoring and control -> Delivery and review
```

### Project and the importance of project management

A **project** is a **non-routine**, **planned**, **specific** task with a **predetermined time span**, carried out for **someone else**, involving **several specialisms**, often in **several phases**, with **constrained resources**, and often **large or complex**.

**Software projects versus other projects:**

- **Invisibility:** progress in software is not immediately visible.
- **Complexity:** software has more complexity per unit of cost.
- **Conformity:** software must conform to the needs of human clients, who are often inconsistent.
- **Flexibility:** software is easy to change, so it is expected to absorb change.

Many software projects fail through poor estimation, unclear requirements, lack of quality standards, and poor monitoring. Good project management addresses these.

### Contract management

When work is done by an **external supplier**, the relationship is controlled by a **contract**. The client's project manager must agree the contract, monitor the supplier's progress and the quality of deliverables, and manage changes. Contract management ensures both sides meet their obligations.

### Activities covered by software project management

1. **Feasibility study:** is the project worth starting? (Development and operational costs versus benefits.)
2. **Planning:** an outline plan for the whole project and detailed plans for the first stage.
3. **Project execution:** design and implementation activities (requirements analysis, design, coding, testing, installation).

The **software development life cycle (SDLC)** activities: requirements analysis (elicitation, analysis, specification), architecture design, detailed design, coding and testing, integration, qualification testing, installation and acceptance support.

### Plans, methods and methodologies

- A **method** is a general way of carrying out a type of activity (for example, a testing technique).
- A **plan** turns a method into specific activities with dates and people.
- A **methodology** is a group of methods used together (for example, an object-oriented methodology).

### Ways of categorising software projects

- **Compulsory versus voluntary users** (an internal payroll system versus a game).
- **Information systems versus embedded systems.**
- **Software products versus services** (generic packages versus bespoke systems).
- **Outsourced projects** (part of the work given to an external company).
- **Objective-driven versus product-driven** development (the client states a problem and objectives, versus a precise specification).

### Stakeholders

People with a stake in the project:

- **Internal to the project team** (under the project manager's direct control).
- **External to the team but in the same organisation** (for example, users in another department).
- **External to the organisation** (customers, suppliers, regulators).

The project manager must communicate with all of them. **Boehm's Theory W** ("make everyone a winner") aims to satisfy every stakeholder.

### Setting objectives

**Objectives** state what the project should achieve and are owned by a **project authority** (steering committee). Good objectives are **SMART**:

- **S**pecific
- **M**easurable
- **A**chievable
- **R**elevant
- **T**ime constrained

**Sub-objectives** and **goals** break a large objective into steps.

### The business case

A **business case** justifies the project. It includes the background, the proposed project, market (for products), organisational and operational changes, benefits, outline of the implementation plan, costs, financial case (cost–benefit), and risks.

### Project success and failure

- A project is **successful** if it delivers the agreed functionality, with the required quality, on time and within budget.
- **Business success** depends on whether the delivered system actually brings the expected benefits to the organisation.
- Common failure causes: unclear objectives, poor estimation, poor communication, uncontrolled scope creep, insufficient user involvement.

### Management and management control

**Management** involves: planning, organising, staffing, directing, monitoring, controlling, innovating and representing.

**Management control** is a cycle:

```flow
Set objectives -> Collect data on progress -> Process into information -> Compare with targets -> Decide and take corrective action -> Modify the plan
```

### Project management life cycle

- **Project initiation:** feasibility study and approval.
- **Project planning:** estimate effort, schedule, staffing, risk and quality plans.
- **Project execution:** carry out the work.
- **Project monitoring and control:** compare actual progress with the plan and correct deviations.
- **Project closing:** deliver, release resources, record lessons learned (post-implementation review).

### Traditional versus modern project management practices

| Aspect | Traditional | Modern |
|---|---|---|
| Planning | Detailed plan up front | Plan incrementally, refine as you go |
| Requirements | Fixed early | Expected to change |
| Delivery | One big delivery at the end | Frequent small deliveries |
| Customer | Involved mainly at the start and end | Involved throughout |
| Quality | Checked by testing at the end | Built in at every step |

### Project evaluation

**Strategic assessment:** does the project fit the organisation's strategy? Programme management looks at a group of projects together.

**Technical assessment:** is the required technology available and compatible with the existing environment?

**Cost–benefit analysis:**

1. Identify all **costs**: development costs, setup costs (hardware, training), operational costs.
2. Identify all **benefits**: direct (lower costs), assessable indirect (fewer errors), intangible (better morale).
3. Express both in money over the project's life to get the **cash flow**.

### Cost–benefit evaluation techniques

- **Net profit** = total income − total costs, over the life of the project. Ignores timing.
- **Payback period:** the time taken to break even. Shorter is better. Ignores income after payback.
- **Return on investment (ROI)** = (average annual profit ÷ total investment) × 100. Ignores timing.
- **Net present value (NPV):** discounts each year's cash flow to today's value:
  - discount factor = 1 / (1 + r)^t, where r is the interest (discount) rate and t the year
  - NPV = Σ (cash flow in year t × discount factor)
  - A positive NPV means the project is worth doing at that rate.
- **Internal rate of return (IRR):** the discount rate that makes NPV = 0. Compare it with the cost of borrowing.

**Worked NPV example:** a project costs 100,000 now and returns 30,000 a year for 5 years. At r = 10%, the discount factors are 0.909, 0.826, 0.751, 0.683 and 0.621. The present value of returns is 30,000 × 3.790 = 113,700, so NPV = 113,700 − 100,000 = **+13,700**. The project is worth doing at 10%.

### Risk evaluation

- **Risk identification and ranking:** list the risks, and score each by **importance** (impact) and **likelihood**.
- **Risk and NPV:** a riskier project needs a higher discount rate (a **risk premium**).
- **Cost–benefit with probabilities:** expected value = Σ (probability × outcome).
- **Decision trees:** show the options and their probable outcomes, so the option with the best expected value can be chosen.

## Module 5 — Software quality and project estimation

> **In short:** **quality** means the software does what users need, reliably, and is easy to maintain. Quality **models** (McCall, ISO 9126) list the characteristics to measure. **Estimation** predicts the effort, time and cost of a project, using decomposition (lines of code, function points) or empirical models such as **COCOMO**.

```flow
Estimate size (LOC or FP) -> Apply a productivity or empirical model -> Effort (person-months) -> Schedule and staffing -> Cost
```

### Software quality in project planning

Quality is planned, not added at the end. In **Step Wise** project planning, quality concerns enter at several points:

- identify the installation standards and procedures (step 1)
- identify the project's quality requirements (step 2)
- identify activities and quality checks for each product (step 5)
- review quality plans as the project progresses

### Importance of software quality

- Software is increasingly **critical** (banking, medicine, transport).
- Its quality is hard to judge from the outside (**invisibility**).
- Errors found late are **expensive** to fix, and errors found by users damage trust.

### Defining software quality

Quality must be defined as **measurable** characteristics. For each quality, state:

- a **definition**
- a **scale** (the unit of measurement)
- a **test** (how to measure it)
- the **minimally acceptable** level, the **target** and the **current** value

Examples: **availability** (percentage of time the system is usable), **mean time between failures (MTBF)**, **failure on demand**, **support activity** (number of fault reports).

### Software quality models

- **McCall's model:** quality factors grouped into three views.
  - **Product operation:** correctness, reliability, efficiency, integrity, usability.
  - **Product revision:** maintainability, flexibility, testability.
  - **Product transition:** portability, reusability, interoperability.
- **Dromey's model:** links product properties to quality attributes.
- **Boehm's model:** a hierarchy from high-level uses (as-is utility, maintainability, portability) down to primitive characteristics.
- **ISO 9126:** six characteristics, each with sub-characteristics:

| Characteristic | Meaning |
|---|---|
| Functionality | Does it provide the required functions? |
| Reliability | Does it keep working under stated conditions? |
| Usability | Is it easy to learn and use? |
| Efficiency | Does it use time and resources well? |
| Maintainability | Is it easy to change and fix? |
| Portability | Can it move to another environment? |

ISO 9126 has since been replaced by **ISO/IEC 25010**, which adds security and compatibility as separate characteristics.

### Product versus process quality management

- **Product quality management** measures the quality of the products (code, documents) through reviews and testing.
- **Process quality management** improves the **process** that makes the products, on the idea that a good process produces good products. Examples: ISO 9001, CMMI.
- **Capability Maturity Model (CMM) levels:** 1 Initial, 2 Repeatable, 3 Defined, 4 Managed, 5 Optimising.

### Observations on estimation

- Estimates are needed to plan, staff and price a project, but they are **uncertain**, especially early.
- Common problems: novel applications, changing technology, lack of homogeneity of project experience, subjective estimates, political pressure.
- **Over-estimates** may make the work expand to fill the time (Parkinson's law); **under-estimates** cause hurried, low-quality work.
- Base estimates on **past data** from similar projects where possible.

### Decomposition techniques

Break the project into smaller pieces, estimate each, and add them up.

- **Software sizing:** fuzzy-logic sizing, function-point sizing, standard-component sizing, change sizing.
- **Problem-based estimation:**
  - **LOC (lines of code) based:** estimate the LOC of each function (optimistic, most likely, pessimistic), compute the expected value, then divide by productivity (LOC per person-month).
  - **Expected value** = (optimistic + 4 × most likely + pessimistic) ÷ 6.
  - **FP (function point) based:** count the information domain values below, apply complexity weights, and adjust.
- **Process-based estimation:** estimate the effort for each process activity (communication, planning, modelling, construction, deployment) for each function.
- **Use-case based estimation:** estimate from the number and complexity of use cases.

**Function points:**

| Information domain value | Simple | Average | Complex |
|---|---|---|---|
| External inputs (EI) | 3 | 4 | 6 |
| External outputs (EO) | 4 | 5 | 7 |
| External inquiries (EQ) | 3 | 4 | 6 |
| Internal logical files (ILF) | 7 | 10 | 15 |
| External interface files (EIF) | 5 | 7 | 10 |

FP = count total × [0.65 + 0.01 × Σ Fᵢ], where the Fᵢ are 14 value adjustment factors, each rated 0 (no influence) to 5 (essential).

### Empirical estimation models

An empirical model predicts effort from size using a formula fitted to data from past projects: **E = A + B × (ev)^c**, where ev is the estimation variable (LOC or FP).

**COCOMO (Constructive Cost Model, Boehm):** basic COCOMO estimates effort in person-months from size in KLOC:

| Project type | Effort E (person-months) | Development time D (months) |
|---|---|---|
| Organic (small team, familiar problem) | 2.4 × (KLOC)^1.05 | 2.5 × E^0.38 |
| Semi-detached (mixed experience) | 3.0 × (KLOC)^1.12 | 2.5 × E^0.35 |
| Embedded (tight constraints) | 3.6 × (KLOC)^1.20 | 2.5 × E^0.32 |

Average staff = E ÷ D.

**Worked example:** an organic project of 32 KLOC: E = 2.4 × 32^1.05 ≈ 2.4 × 38.1 ≈ 91 person-months; D = 2.5 × 91^0.38 ≈ 2.5 × 5.55 ≈ 13.9 months; average staff ≈ 91 ÷ 13.9 ≈ 6.6 people.

**COCOMO II** has three stages of models: application composition (using **object points**), early design, and post-architecture. It adjusts effort with **scale factors** and **cost drivers**.

## Exam tips

- **Process models** are asked every year: draw the waterfall, incremental, prototyping and spiral diagrams, and compare them (when to use, advantages, drawbacks).
- Learn the **seven requirements engineering tasks** in order, and be ready to write a **use case** for a given system (for example, an ATM or library) with actor, preconditions, scenario and exceptions.
- For agile, know the **Agile Manifesto values**, the **four XP activities** and the **Scrum** roles and meetings.
- Practise **NPV, payback and ROI** numericals, and one **COCOMO** or **function point** calculation, showing the formula and every step.
- Know **McCall's** three groups and the six **ISO 9126** characteristics, with one line on each.
